## Measured facts (S2.4 L1 discharge — measured at breakdown, never believed)

All ClickHouse measurements taken 2026-08-23 against the exact compose-pinned image `clickhouse/clickhouse-server:26.3.17.110`, the three real migrations applied verbatim, ~2.1M seeded span rows + ~1.07M log rows across 2 workspaces × 89 days (12k spans + 6k logs per workspace-day), spans flowing through the real `trace_summaries_mv`.

### CH1 — lightweight `DELETE FROM` works on all three engines, per-workspace, immediately visible
- `DELETE FROM obstack.spans WHERE workspace_id='w_free' AND start_time < now() - INTERVAL 7 DAY`: **996,000 rows masked in 8.37s**; 72,000 inside-tier rows kept; the other workspace's 1,068,000 rows untouched; a SELECT immediately after sees 0 past-cutoff rows.
- Same on `logs` (which carries the `bloom_filter` skip index): **4.99s**, exact split preserved.
- Same on `trace_summaries` (**AggregatingMergeTree** — the engine the phase plan flagged as a measured question): works, **0.075s**, predicate on `max_seen_date`.
- Mechanism observed in `system.mutations`: lightweight DELETE = `UPDATE _row_exists = 0` mutation; all completed (`is_done=1`).
### CH2 — `ALTER TABLE … DELETE` (mutation) also works: 6.72s synchronous (`mutations_sync=2`) for ~708k rows. Heavier (part rewrite vs mask). **The sweep uses lightweight DELETE**; `ALTER` is the documented fallback.
### CH3 — disk reclaim is merge-time, visibility is immediate: after the deletes, `system.parts` still holds 1,416,000 span rows vs 420,000 visible. Product truth ("data past your tier is gone from the product") is immediate; bytes reclaim at merge. Stated in the operator docs S4.4 writes.
### CH4 — TTL is enforced at insert-time part formation: 1,000 rows aged 40 days inserted into a 30-day-TTL table land as **0 rows** — dropped forming the part, before any merge. Consequences: (a) the outer-TTL widening migration must land **before** the receivers, or any late-timestamped payload older than 30d silently vanishes; (b) today's 30d TTL already silently drops >30d-late timestamps — the widening fixes exposure for 30–90d.
### CH5 — `MODIFY TTL` alone does NOT retro-apply at merge (narrowed TTL + `materialize_ttl_after_modify=0` + `OPTIMIZE FINAL` → all 1,000 rows survive). The default auto-`MATERIALIZE TTL` mutation (observed firing on our three `MODIFY TTL`s) is what recalculates existing parts. Widening 30→90 with all live data ≤30d old: nothing eligible, safe; the materialize mutation is the migration's cost and completed instantly at our scale.
### CH6 — grants: `obstack_ingest` can lightweight-DELETE (measured) but has **no `system.parts`/system-table SELECT** (measured ACCESS_DENIED). The sweep therefore must not read system tables — and does not need to.
### VD — Vercel log drain (docs measured 2026-08-23; vercel.com/docs/drains/reference/logs last_updated 2026-07-01, /docs/drains/using-drains 2026-07-22, /docs/drains/security 2026-07-29)
- Delivery: HTTPS POST, batched; encodings **json** (array of log objects) and **ndjson** (one object per line); optional **gzip** compression; `user-agent: VercelDrain/1.0 (+https://vercel.com/docs/drains)`. Endpoint must answer **200 OK**; drain creation fires an automatic test delivery (`POST /v1/drains/test` exists) — **no `x-vercel-verify` challenge exists in the current Drains flow** (that was the deprecated log-drains API; the receiver need not implement it, and answering 200 to the test delivery IS the verification).
- Auth: **custom headers are supported per-drain** — the operator sets `Authorization: Bearer <obstack key>`, which is exactly the D98 path D254 requires. Optional `x-vercel-signature` = **HMAC-SHA1 hex over the raw body** with the drain's signature secret (vendor-documented verification code cited); support decided in kickoff item K3.
- Log entry fields (full schema captured): required `id`, `deploymentId`, `source` (enum build|edge|lambda|static|external|firewall|redirect), `host`, `timestamp` (unix **ms**), `projectId`, `level` (enum info|warning|error|fatal); optional `message` (≤256KB, may truncate), `path`, `statusCode`, `requestId`, `environment`, `branch`, `projectName`, `executionRegion`, `type`, and **`traceId`/`spanId` (plus dotted `trace.id`/`span.id` duplicates)** — auto-enriched when Vercel Tracing is on. `proxy` object for request logs.
- **Correlation posture (D254 discharge): `traceId`/`spanId` are measured payload fields that actually carry trace context — extracted; everything else lands trace-less and joins as the nearby class (D37 window). No other field is inferred into context.**
- Failure semantics: >80% failures or >50 failures/hour → drain flagged errored + email; sustained failure can disable the drain. The receiver answers 200 fast and never blocks on ClickHouse (the existing consume path already guarantees this).
### CW — CloudWatch subscription filter → Lambda (AWS docs measured 2026-08-23, docs.aws.amazon.com/AmazonCloudWatch/latest/logs/SubscriptionFilters.html)
- Lambda receives `{ "awslogs": { "data": "<base64(gzip(JSON))>" } }`; decoded: `{ owner, logGroup, logStream, subscriptionFilters[], messageType, logEvents: [{ id, timestamp(ms), message }] }`.
- `messageType` is `DATA_MESSAGE` or **`CONTROL_MESSAGE`** ("mainly for checking if the destination is reachable") — the forwarder must succeed on CONTROL_MESSAGE without POSTing.
- `logEvents[].message` is a raw string. **No trace-context field exists in the envelope** — CloudWatch-delivered logs land trace-less, joining as the nearby class. No inferred correlation (D254).
- Setup surface (documented for the operator doc): `aws lambda create-function` + `aws lambda add-permission --principal logs.amazonaws.com` + `aws logs put-subscription-filter --destination-arn <lambda>`; standard pattern, no SAM/Terraform (D254 refusal stands).
