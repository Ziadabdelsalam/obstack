## 1. Q1 — The endpoint: where it lives, how it authenticates, what a 2xx means

- **D493 — `POST /v1/changes` on the ingest binary's receiver mux (the OTLP/HTTP listener, `:4318`), beside `/v1/integrations/*`.** Auth is the existing `Authorization: Bearer <api key>` → `auth.Authenticator.Workspace` → `Identity{WorkspaceID, KeyID}`, unchanged; every refusal of a missing/unknown/revoked key is the D6 collapse (401, `WWW-Authenticate: Bearer`, `{"error":"missing or unknown API key"}`). Why ingest and not web: an API key is the ingest's credential class — "it names the workspace every record in that request is written into" (0004) — web holds only session auth, the integrations precedent already lives on this mux, the keystore's fail-static cache is already there, and the recipe then targets the SAME host and header the quickstart documents. One credential class per binary; web never writes on behalf of a bearer token.
- **D494 — request shape: one JSON object per request; `Content-Type: application/json` required (415 otherwise, the OTLP `requestEncoding` message shape); body capped at 64 KiB by `http.MaxBytesReader` (413 `payload is over the 64KiB limit` — the 16 MiB OTLP cap is for telemetry batches, not an annotation); gzip not accepted.** Batches are pre-registered (`[]` bodies refused with the field named), not built: the GHA step posts one event, and backfill is not a v1 use case.
- **D495 — a 2xx is a durable fact.** The row is INSERTed synchronously in the request (one `$n`-bound statement, `workspace_id` and `key_id` from the identity, NEVER from the body), and the response is `201 {"id":"chg_…","deduplicated":false}`. If Postgres refuses or is unreachable the answer is `503 {"error":"storage unavailable"}` — never a 200-then-lost. No batcher, no writer queue: the S1 writer exists for telemetry volume; a change event is small and rare, and a CI step that gets a 2xx must be able to trust it.
- **D496 — idempotency by client-supplied `external_id`.** Optional, ≤ 200 chars; `UNIQUE (workspace_id, external_id) WHERE external_id IS NOT NULL`. A repeat POST carrying an `external_id` the workspace already holds answers `200 {"id":"<the ORIGINAL row's id>","deduplicated":true}` and changes NOTHING — first write wins, the second body is discarded, never merged (refuse-never-upsert holds; an at-least-once client gets a safe retry). Without `external_id` every POST is a new row — the honest default. The recipe's `external_id` is `github:<repository>:run:<run_id>:<run_attempt>`: a retried step dedupes, a re-run job (a new attempt) is a new deploy.
- **D497 — change events do not meter, do not sample, and are never quota-refused (the D365 posture).** They never touch `usage_ledger`; `OverQuota` does not apply (an over-quota window is exactly when a deploy annotation matters). Ops truth still lands: an accepted event adds 1 to the key's health `accepted` (the `RecordAcceptedMetrics` health-only path — the settings page's key liveness then reflects the deploy hook), a 400 adds 1 to `dropped_decode`; refusals also count on `obstack_ingest_changes_refused_total{reason=decode|invalid|rate_limited|storage}` beside `obstack_ingest_changes_accepted_total{kind}` and `obstack_ingest_changes_deduplicated_total` (the `obstack_ingest_<domain>_<noun>_total` house prefix). No new health column, no migration to 0007/0008.
- **D498 — the abuse guard is a per-workspace rate cap, refused not sampled.** In-process token bucket per workspace: 60 events/min sustained, burst 60; over it → `429 {"error":"change events are capped at 60 per minute per workspace"}` + `Retry-After: 60`. Replicas each hold their own bucket, so the effective cap is N× — stated, acceptable for a guard that is not a billing unit. This is the first hard refusal on the receive path (telemetry degrades by sampling; an annotation feed is not a firehose and a refused write is honest where a silently thinned one is not). Growth is then bounded by rate × retention (D501).

## 2. Q2 — The event document (strict, six kinds, two timestamps)

- **D499 — the wire document, unknown fields REFUSED.** `json.Decoder.DisallowUnknownFields` — the first strict decoder in the service, by design: the Vercel/CloudWatch routes are permissive because they decode third parties' payloads; this is OUR contract, and a typo'd field name in a CI recipe silently dropping the deploy's service is the D13 failure mode for a write API. Fields (all strings trimmed, valid UTF-8, control characters refused except `\n` in `detail`; every refusal is `400 {"error":"<field>: <reason>"}` naming the field):
  - `kind` REQUIRED, one of the six.
  - `title` REQUIRED, 1–200.
  - `detail` optional ≤ 2000, default `""`.
  - `who` optional ≤ 120, default `""` (the recipe sends `GITHUB_ACTOR`).
  - `service` optional ≤ 120 — the deploys panel joins on EQUALITY with the trace-derived service name (`spans.service` is the identity, D367); NOT validated against the catalog (a first deploy precedes the first span, honestly).
  - `ref` optional ≤ 128 — a sha, tag or version; the panel's first column.
  - `source` optional ≤ 60 — where the event came from (`github-actions`); rendered as a small label so a reader can tell sources apart once more than one exists (the catalog-gated future).
  - `at` optional RFC 3339; default = server `now()`; refused if more than 5 minutes in the future; any past time accepted (a backfilled history is honest history). Stored as `at`; the server's receipt time is ALWAYS stored as `created_at`.
  - `link` optional `{label ≤ 60, href}` — `href` must parse as an ABSOLUTE `http`/`https` URL ≤ 2048 (anything else refused: `javascript:`/`data:` never reach a DOM); rendered as an external anchor (`rel="noopener noreferrer"`, new tab) — the live link points OUT to the source system, the opposite of the mock's product-internal links.
  - `external_id` optional ≤ 200 (D496).
  - The body cannot name a workspace or a key — those are unknown fields, refused (tenancy from the credential only).
  - The DDL is the authority for every length (D500 CHECKs); Go refuses first with the field named so the constraint never surfaces as a 500. The kind vocabulary and the field NAMES are pinned across three places by one D385-style source-parsing test (Go struct tags ↔ `lib/change-types.ts` ↔ the docs page's field table) — no fourth copy, no drift.
- **Secrets stay out by policy, not by magic:** a `kind: "secret"` event describes a rotation; the endpoint stores what it is given and renders every field to every member of the workspace. The docs page says so in one sentence beside the field table ("never put the secret's value in the event"). No redaction pass — pretending to scrub would be the D13 violation.

## 3. Q3 — DDL, retention (a carry-forward), tenancy

- **D500 — `pgmigrations/0011_change_events.sql`, 0009/0010 house style.** One table, `change_events`: `id TEXT PRIMARY KEY` (`chg_` prefix, the alerts three-prefix pattern), `workspace_id` FK → workspaces ON DELETE CASCADE, `key_id TEXT NULL` FK → api_keys ON DELETE SET NULL (provenance for ops and the future audit — which credential posted it; never rendered in v1), `kind TEXT NOT NULL CHECK (kind IN (six))`, `title TEXT NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200)`, `detail TEXT NOT NULL DEFAULT '' CHECK (char_length(detail) <= 2000)`, `who TEXT NOT NULL DEFAULT '' CHECK (<= 120)`, `service TEXT NULL CHECK (<= 120)`, `ref TEXT NULL CHECK (<= 128)`, `source TEXT NULL CHECK (<= 60)`, `link_label TEXT NULL CHECK (<= 60)`, `link_href TEXT NULL CHECK (<= 2048)` with `CHECK ((link_label IS NULL) = (link_href IS NULL))`, `external_id TEXT NULL CHECK (<= 200)`, `at TIMESTAMPTZ NOT NULL`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. CHECK never enum; no UNIQUE on a name (events are not named). Indexes: `(workspace_id, at DESC)` — the feed; `(workspace_id, service, at DESC) WHERE kind = 'deploy'` — the deploys panel; `UNIQUE (workspace_id, external_id) WHERE external_id IS NOT NULL` — D496. Pins: the `qa_a6` applied-set string gains `,0011_change_events`; idempotency proven raw (psql double-apply) and through the runner (the T1 S7.1 pattern).
- **D501 — Postgres retention is built ONCE here, and it pays the S7.1 debt (amends D489 on the record).** Finding: D489 ruled "`retention.go` gains `alert_events` in its per-workspace plan-window sweep"; the S7.1 breakdown assigned that half to no task and the integrator did not check it — `retention.go:128-138` still holds six ClickHouse deletes and no Postgres delete, and `alert_events` has no expiry beyond FK cascades today. S7.1 ship-log defect, registered here. Ruling: the sweeper's per-workspace pass (same `plansSQL`, same `retention_days` window, same cadence) gains a Postgres leg over BOTH tables — `alert_events` by `created_at`, `change_events` by `at` (retention is "how far back the product shows"; a backfilled event older than the window is honestly outside it) — deleted in bounded batches (`ctid IN (SELECT ctid … LIMIT 5000)` loops until zero, the ClickHouse leg's chunking spirit), one statement timeout each, counted on the sweeper's existing per-table counters. Proven red: a second workspace's rows are untouched by the first's sweep; a row inside the window survives; a row outside it goes. No per-workspace row cap in v1 — the bound is D498's rate × the plan window.
- **Tenancy (D7/D11, binding):** `workspace_id` comes from `Identity` on write and is `$1`-bound on every read (`listChangeEvents`, `listServiceDeploys`, the sweep); proven red per path — a second workspace's key posts an event and the first workspace's feed and panel never show it, AND the inverse. The dedupe key is scoped by workspace by construction (the partial UNIQUE includes it — two workspaces may share an `external_id` string).
