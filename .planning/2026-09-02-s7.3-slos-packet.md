## 1. Q1 — What is measured (the indicator, honestly)

- **D505 — the unit is the TRACE, read from `trace_summaries` with the S7.1 trace leg's exact shape.** A trace is a request; availability and latency are properties of requests. `good` and `total` are counted per MERGED trace (GROUP BY workspace_id, trace_id with the house combinators, never FINAL, `max_seen_date` prune in WHERE, the exact window bound on merged `min_start` in HAVING — `eval_trace.go:51-76` verbatim, widened to days): availability `good` = `error_count = 0` (a trace with no error span); latency `good` = `duration_ms <= thresholdMs`, where a trace's duration is merged `max_end − min_start` — the S7.1 p95's own definition, so the SLO and the alert can never disagree about how long a trace took. SLI = good / total × 100. Stated, not smoothed: this is a DIFFERENT number from `services.ts`'s span-grained error rate (error spans over spans), for the same reason `eval_trace.go:14-34` states for p95 — a request-level objective counts requests, and the card's objective sentence says "traces" so the reader is told which. No new ClickHouse table, no rollup, no `spans` scan (a 30-day scan of raw spans for one number is the wrong tier; `trace_summaries` is the aggregate the phase plan's "over existing aggregates" names).
- **D506 — scope v1 = `service: string|null`, the trace leg's predicate verbatim** (`has(groupUniqArrayArray(services), ?)` — traces that INVOLVE the service, the documented caveat carried over). Route scoping (the mock's `POST /v1/chat`, which `root_name` could answer) is pre-registered, not built: the fence reads "the mocked shapes" as the SLI kinds, and a second predicate is a second proof and a second editor field.
- **D507 — windows are `7d | 30d` rolling, `[now − window, now)`; retention clips the window HONESTLY.** The evaluator reads what the store holds, and the store holds what the plan's sweep left (free = 7 days, pro = 30): a 30-day SLO on a free workspace is computed over 7 days of data BY CONSTRUCTION, and the number is true of those 7 days. The card says so: when the workspace's `retention_days` < the window's days, the window label reads `30d · 7d retained on Free` (the plan row read through the existing `usage.ts` join, on the page's own request). Never "30 days" over 7 days of data (D13). A 1d window is not offered — a day is what an alert rule is for (D482's vocabulary).
- **D508 — no-data is a STATE, not a number.** `total = 0` ⇒ `status = 'no-data'`, `current_pct`/`budget_burned_pct` NULL, the card renders `NO DATA` and a dash where the percentage would be, and no event is produced entering or leaving it (nothing measured is not news — the D480/evalsNoData posture). A workspace whose first trace has not arrived sees an honest card, not 100%.

## 2. Q2 — Budget, status, cadence, events

- **D509 — the arithmetic, one definition, in Go with a TS mirror for the editor's preview only.** `bad = total − good`; `allowed = total × (100 − target) / 100`; `current_pct = good / total × 100`; `budget_burned_pct = bad / allowed × 100` (unbounded above — 10 traces at a 99.9% target with one bad is 10,000% consumed, and that is the truth; the BAR is clamped at 100%, the NUMBER is not). Status, decided on counts, strict at the boundary (the `crossed` posture — sitting exactly on the budget is not over it): `breached` iff `bad × 100 > total × (100 − target)`; else `at-risk` iff `budget_burned_pct >= 75`; else `healthy`. The 75 is `AtRiskBudgetPct`, one constant — the mock page's own colour threshold — pre-registered as a per-SLO option, not built. No burn-RATE alerting (multi-window fast/slow burn) in v1: the mock has none and it is a second state machine; pre-registered.
- **D510 — the SLO evaluator is a second claim on S7.1's ticker, in the same package, on the same connections.** `alerting.Evaluator` gains `EvaluateDueSLOs(ctx)` (exported for the drive and the tests, the `EvaluateDue` reason) and its 60-second tick runs both claims in turn; SLOs claim with `SELECT … FROM slos WHERE enabled AND next_eval_at <= now() ORDER BY next_eval_at LIMIT $1 FOR UPDATE SKIP LOCKED` (D478 verbatim, its own transaction), read ClickHouse, write the measurement columns + status + any transition event INSIDE that transaction, then reschedule `next_eval_at = now() + 5m` (`SLOEvalInterval`, its own constant: a 30-day scan every minute for a number that moves by the hour is waste, and the drive proves the tick directly, not the cadence). Per-eval statement timeout 30s (`sloEvalTimeout` — a 30-day merge is bigger than a 1-hour one; still a bound, still fail-open). Fail-open per D480: a ClickHouse error/timeout or an unparseable indicator leaves status and measurements UNCHANGED, advances `next_eval_at`, and counts `obstack_ingest_slo_evals_failed_total`; an empty window counts `obstack_ingest_slo_evals_nodata_total` and takes the D508 state. Cost bound, stated: ≤ `MAX_SLOS_PER_WORKSPACE` (50, D513) merges of ≤ 30 days of `trace_summaries` per workspace per 5 minutes; if `slo_evals_failed_total` ever moves in production on timeouts, an hourly good/total rollup is the pre-registered answer — not a wider timeout.
- **D511 — SLO transitions ride the S7.1 pipeline unchanged; the channel is optional; no channel ⇒ no event row.** A transition INTO `breached` inserts an `alert_events` row at `critical`, INTO `at-risk` at `warning`, and back to `healthy` from either at `info` — severities FIXED by the transition (the status carries its own loudness; an author picking `info` for a breach would be picking a quieter truth), with `slo_id` set, `rule_id` NULL, and `channel_id` captured at emit (D491). `at-risk → breached` and `breached → at-risk` are transitions too (one event each); staying put emits nothing (D484's stuck-horn rule); `no-data` is silent both ways (D508). An SLO with `channel_id NULL` is computed and rendered but produces NO event rows: a `pending` row with nowhere to go would be marked `failed` by the deliverer and rendered as "delivery failed" — a delivery nobody asked for, reported as broken. The card carries `last_transition_at` ("breached since 2026-09-02 10:14 UTC") so the status has a history without a feed row; an in-product SLO history is pre-registered. Web performs no egress and inserts no events — the evaluator is the only writer of SLO events.
- **D512 — the deliverer and the payload learn `slo` additively.** `claimPendingSQL` gains `LEFT JOIN slos s ON s.id = e.slo_id` (`FOR UPDATE OF e` unchanged); `payloadFor` sets a new top-level `slo: {name, objective, status} | null` beside `rule` (null on SLO events; `slo` null on rule and test events) — `PayloadVersion` stays 1 (additive evolution, `payload.go:22-28`); Slack's `{text}` is unchanged in shape (title + detail carry the story). Event text is composed in Go from the parsed indicator and the measured counts (the `event_text.go` seam, stated again: a different artifact from the product's formatter): title `<name>: breached — 98.40% against a 99% target`, detail `<objective sentence>: 98.40% over the last 30d (1,234 of 1,254 traces good); 160% of the error budget consumed.`; resolution title `<name>: healthy again`. `link` NULL in v1 (the `insertEventSQL` reasoning holds: no configured base URL). The feed renders `slo: <name>` where it renders `rule: <name>` today, from the new row fields.

## 3. Q3 — DDL, retention, tenancy

- **D513 — `pgmigrations/0012_slos.sql`, 0010/0011 house style, and the track's FIRST `ALTER TABLE`.** `slos`: `id TEXT PRIMARY KEY` (`slo_` prefix, the `rule_`/`chan_`/`chg_` idiom), `workspace_id` FK → workspaces ON DELETE CASCADE, `name TEXT NOT NULL CHECK (name <> '')`, `indicator JSONB NOT NULL CHECK (jsonb_typeof(indicator) = 'object')`, `target NUMERIC(6,3) NOT NULL CHECK (target > 0 AND target < 100)`, `"window" TEXT NOT NULL CHECK ("window" IN ('7d','30d'))`, `channel_id TEXT NULL REFERENCES notification_channels (id) ON DELETE RESTRICT` (refuse-never-cascade, the 0010 reasoning; `deleteNotificationChannel` counts SLOs beside rules and refuses with the same sentence shape), `enabled BOOLEAN NOT NULL DEFAULT true`, `status TEXT NOT NULL CHECK (status IN ('healthy','at-risk','breached','no-data')) DEFAULT 'no-data'`, `current_pct DOUBLE PRECISION NULL`, `budget_burned_pct DOUBLE PRECISION NULL`, `good_count BIGINT NULL`, `total_count BIGINT NULL` with `CHECK ((good_count IS NULL) = (total_count IS NULL))`, `evaluated_at TIMESTAMPTZ NULL`, `last_transition_at TIMESTAMPTZ NULL`, `next_eval_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `created_at`/`updated_at`; `UNIQUE (workspace_id, name)`; index `(next_eval_at) WHERE enabled` (the claim's shape). Then `ALTER TABLE alert_events ADD COLUMN IF NOT EXISTS slo_id TEXT NULL REFERENCES slos (id) ON DELETE CASCADE` (an SLO event has no meaning once its SLO is gone — the rule precedent), a partial index `(slo_id) WHERE slo_id IS NOT NULL` (the cascade's own lookup), and the exclusivity constraint `CHECK (rule_id IS NULL OR slo_id IS NULL)` added under a `pg_constraint` existence guard (Postgres has no `ADD CONSTRAINT IF NOT EXISTS`; the guard is what keeps the raw double-apply a no-op — proven the T1 way, psql twice + the runner). Why a column and not an `slo_events` table: the phase plan says events go THROUGH the S7.1 pipeline, and a second table would need a second deliverer claim, a second feed read and a second retention leg for the same document. Pins: the `qa_a6` applied-set string gains `,0012_slos`. Cap: `MAX_SLOS_PER_WORKSPACE = 50`, counted under the lock (the D489 shape; the number is D510's cost bound, not a product limit anyone will meet).
- **Retention — nothing new.** SLO events are `alert_events` rows and D501's sweep already cuts them on `created_at`; `slos` rows are definitions and are never swept. The `retention` docs page names no product table and needs no edit.
- **Tenancy (D7/D11, binding):** `workspace_id` from the session on every web statement, `$1`-bound (`server/slos.ts`, the `alerts.ts` rule); a `channelId` from another workspace answers `NO_SUCH_CHANNEL` (D440 shape); the claim is workspace-blind BY DESIGN (D478 — it schedules; stated so nobody "fixes" it); the ClickHouse read is `workspace_id = ?` first. ## 6. Calls flagged for ruling (the S7.2 "six flagged calls" shape — a yes/no each; "as drafted" ratifies all)

- **(a) D505 — trace-grained SLIs** (a request = a trace; availability = no error span in the trace; latency = trace duration ≤ threshold), deliberately NOT the span-grained error rate `services.ts` renders. Alternative: span-grained over `trace_summaries`' merged `error_count/span_count` — matches the services page's number but makes "99.9% of requests" a sentence about spans.
- **(b) D506/D507 — scope = service only; windows = 7d/30d only.** Alternative: add `root_name` (route) scoping now — one more predicate, one more editor field, one more proof.
- **(c) D511 — channel optional; no channel ⇒ no event rows** (status + `breached since` live on the card). Alternative: always insert events and add a fourth delivery state (`none`) to the CHECK and the feed — more truthful history, wider blast radius on the S7.1 tables.
