## 1. Q1 — The endpoint: where it lives, what carries it, who is let in, and what bounds it

- **D640 — `apps/web/src/app/mcp/route.ts`, serving `/mcp` — OUTSIDE the `/app` shell, and the packet says why twice.** (1) Next forbids a `route.ts` beside a `page.tsx` at one segment (`node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`, "Convention"), so `/app/mcp` cannot carry both the page and the endpoint. (2) The shell's gate is a browser gate — `app/app/layout.tsx:81-102` resolves a session and `redirect("/login")` — and a JSON-RPC client that is redirected to a login page has been lied to with a 200; the endpoint must answer 401 in its own vocabulary (D642). `/mcp` is also, to the character, what `MCP_ENDPOINT_PLACEHOLDER` has advertised since S3.4. The route exports `POST`, `GET` and `DELETE`, each delegating to the transport after the auth and rate-limit checks below — the method matrix (405 for a GET stream in stateless mode, 405 for DELETE with no session) is the SDK's answer, never ours to restate.
- **D641 — the SDK is `@modelcontextprotocol/server` 2.0.0 (the current major; `@modelcontextprotocol/client` 2.0.0 for the drive and the tests), pinned EXACT (D14), with `WebStandardStreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })` constructed PER REQUEST.** Read from the SDK's own docs at 2.0.0: the web-standard transport takes a `Request` and returns a `Response` (the decision rule in its v1→v2 migration guide: a handler that receives a web-standard `Request` uses `@modelcontextprotocol/server`, one that receives Node's `IncomingMessage` uses `@modelcontextprotocol/node` — Next's route handlers are the former, `15-route-handlers.md` "Route Handlers"); `sessionIdGenerator: undefined` is the documented stateless mode (no session id issued, none validated), and `enableJsonResponse` returns plain JSON instead of opening an SSE stream. One `McpServer` + one transport per request, no session store: replica-safe by construction (the `rate-limit.ts` one-replica caveat does NOT apply here), and nothing to sweep. `zod` becomes a DIRECT dependency of `apps/web` at the version already in the tree (4.4.3 transitively; a transitive pin is not a pin) — v2 takes `zod/v4` schemas. The v1 line (`@modelcontextprotocol/sdk` 1.30.0) is the alternative, flagged (g): it works, but v2 removed the deprecated variadic `.tool()` API and made the web-standard transport a first-class export, and a server started on the outgoing major is a codemod owed to nobody.
- **D642 — one credential, one lookup, one answer: `Authorization: Bearer <key>` → `resolveApiKey(token, query)` → `{ keyId, workspaceId, scope } | null`; anything but a hit is a bodiless 401 with `WWW-Authenticate: Bearer realm="obstack"`.** The lookup is ingest's `keystore/store.go:103` restated in TypeScript with the scope clause added: `SELECT id, workspace_id, scope FROM api_keys WHERE token_hash = $1 AND revoked_at IS NULL AND scope IN ('read','setup')` over `hashToken(token)` (`api-keys.ts:75`, the D139 cross-language hash). Unknown, revoked, ingest-scoped and malformed are the SAME 401 (D6: distinguishable answers make the endpoint a key-probing oracle). The SDK ships `requireBearerAuth`/`verifyBearerToken` for OAuth tokens; they are NOT used — ours is an API-key check that runs before the transport sees the request, three lines, and it must not learn a token verifier's vocabulary. **`api-keys.test.ts:119-133` records the module's three calls and asserts `workspace_id` in the text and `params[0] === "ws_a"` per statement; `resolveApiKey` is ADDED to that loop as a fourth case with its own assertion — the statement binds the HASH as `$1` and RETURNS `workspace_id` — and a comment stating why the shape differs: here the workspace is the OUTPUT, and the hash is the owner pin (D148's rule, in the direction ingest already runs it) ⟨rev: the first draft called this an exemption from a module-wide SQL scan that does not exist⟩. No cache: the page-level reads that follow cost more than the lookup, and a cache is a second copy of ingest's fail-static policy (`store.go:224-262`) that this path has no outage story for.
- **D643 — tenancy: the resolved `workspaceId` is the ONLY workspace any tool ever sees, and no tool argument can name one.** The route builds a per-request `McpContext { workspaceId, keyId, scope, ch: forWorkspace(workspaceId), query: queryRows, nowMs: referenceNowMs() }` (`clickhouse.ts:98`, `postgres.ts:31`, `data.ts:89`) and every handler closes over it — the D113 shape, the pages' own. ClickHouse reads go through `ScopedClickHouse`, whose unscoped-SQL tripwire (S3.1, proven red four ways) covers every tool by construction; Postgres reads bind `$1 = workspaceId` exactly as `listIncidents`/`listSlos`/`listAlertEvents` already do. **RED per tool** (`mcp.integration.test.ts`, real Postgres + ClickHouse under the DSN guard): two workspaces, two read keys; every id-taking tool called with the OTHER workspace's id through the FIRST key answers the not-found sentence, and every list tool answers rows of one workspace only — each assertion first proven red by a deliberately unscoped handler in the test's own scratch, then green.
- **D644 — the key class: `services/ingest/pgmigrations/0014_api_key_scope.sql`, ONE guarded ALTER, and both doors refuse the other scope.** `ALTER TABLE api_keys ADD COLUMN IF NOT EXISTS scope TEXT NOT NULL DEFAULT 'ingest' CHECK (scope IN ('ingest','read','setup'))` — the 0012/0013 house style (CHECK never enum; `IF NOT EXISTS` so the double-apply is a no-op, proven raw and through the runner). Every existing key, including `key_dev_local`, is an ingest key after the upgrade, so ingest changes for nobody. Ingest's `lookupSQL` (`store.go:103`) gains `AND scope = 'ingest'` and its keystore test gains the RED (a read key is 401 at `/v1/traces`); the web's `RESOLVE_SQL` carries `AND scope IN ('read','setup')` (D642) — `setup` is `read` plus the one mutation in §6 D666, never a key that ingests. Flagged (b) — the alternatives are priced there. **Why a scope at all, stated once:** an ingest key is a WRITE credential that today lives in an exporter's env; an agent's MCP config is a file on a developer's laptop. Letting either credential do the other's job means a leaked exporter key reads the workspace, and a leaked agent config writes into it. Two scopes cost one column. **Number collision, named:** the S7.5 draft also claims `0014` (`0014_oncall.sql`, its D602). Whichever sprint lands first takes `0014`; the other renumbers at its own breakdown — recorded here so neither packet is edited silently.
- **D645 — bounds: a per-key sliding window at the HTTP layer, and inside the tools ONLY the contracts' own caps.** `rate-limit.ts` widens `RateLimitAction` with `"mcp"` at `MCP_RATE_LIMIT` (120 calls / 60 s), keyed by the KEY ID rather than the IP (the same map, the same window arithmetic, the same one-replica caveat stated at `rate-limit.ts:14-20`, which for `web` is a fact about Railway's one replica and the chart's `web` Deployment alike). The check runs AFTER auth (an unauthenticated flood is bounded by the 401's cost, and an IP-keyed limit on a bearer endpoint would let one key exhaust a NAT's worth of colleagues) and BEFORE the transport: an over-limit call is an HTTP 429 with `Retry-After`, never a JSON-RPC error dressed as a tool result. - **D646 — reads are unmetered, and the one spend on this tree is not a tool.** The ledger counts ingested events (D163, `usage.ts:36-46`) and MCP reads are the pages' reads by another door; nothing here writes `usage_ledger`.
