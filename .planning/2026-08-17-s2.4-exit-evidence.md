## 1. The two traces, in SQL

Selected by shape, not recency: both samples call their own fake model endpoint
over HTTP and both containers are health-checked every five seconds, so each run
leaves a scatter of truthful little `api` traces beside the one that matters.
The harness selects on `countIf(layer='agent') > 0 AND count() >= 4` and
**requires exactly one match**, which turns the selection into an assertion.

```
sdk-sample-py 4e82a24b5c97805de45553fac6b7b2bb
sdk-sample-ts 504ba31813a47588a0d7d3c60d935b7d
```

```
sdk-sample-py, 7 spans                     sdk-sample-ts, 6 spans
api    POST /chat            (server)      api    POST                   (server)
other  POST /chat http recv  (internal)    agent  agent.answer_question  (internal)
agent  agent.answer_question (internal)    tool   tool.knowledge_lookup  (internal)
tool   tool.knowledge_lookup (internal)    other  ai.generateText        (internal)
llm    chat gpt-4o-mini      (client)      llm    chat gpt-4o-mini       (client)
other  POST /chat http send  (internal)    llm    chat gpt-4o-mini       (client)
other  POST /chat http send  (internal)
```

Asserted per trace, each number read out of ClickHouse and compared in the
harness so a failure names the fact that broke:

| claim | py | ts |
|---|---|---|
| ≥ 4 spans under one `trace_id` | 7 | 6 |
| all four layers present (`api`, `agent`, `tool`, `llm`) | yes | yes |
| every `llm` span carries the full D8 set **and** a non-zero cost | 1 of 1 | 2 of 2 |
| the six non-content D8 names arrived as **span attributes** | 1 of 1 | 2 of 2 |
| `obstack.agent.step` and `obstack.tool.name` present | 1 + 1 | 1 + 1 |

The `other` spans are honest: ASGI plumbing on the Python side, the Vercel AI
SDK's outer `ai.generateText` span on the TypeScript side. Two `llm` spans on
the TS trace are the two JS mechanisms — the translated Vercel-AI span and the
patched `openai` client — and extra `llm` spans do not weaken the four-layer
claim (D77(e)).

The wire-shape assertion is worth naming separately: the six names are in the
attributes Map exactly as the SDK sent them, which is what makes this the
span-attribute form D8 mandates rather than the span-EVENT form ingest
deliberately does not read (D38 FINAL). An event-form SDK would land rows that
look stored and read back empty.

## 2. D92's two-part Map assertion, both samples

D8-AMENDMENT / carry-forward 4 says prompt and completion live in the dedicated
ZSTD columns and never in the attributes Map. T4's review found the first half
of that — key absence — passing while the content sat in the Map under upstream
`ai.*` keys. D92 made the assertion two-part, and this run makes both halves on
both samples, each with a positive control so an absence cannot be a mistyped
token:

| assertion | py | ts |
|---|---|---|
| control: the token really is in this run's `prompt`/`completion` columns | 1 prompt, 1 completion | 2 prompts, 2 completions |
| (1) no Map key equals `gen_ai.prompt` or `gen_ai.completion` | 0 spans carry one | 0 spans carry one |
| (2) no Map **value** contains the prompt/completion content, under any key | 0 of 7 spans | 0 of 6 spans |

The tokens are the samples' deterministic fakes: `obstack sample agent` (both
system prompts) and `Based on the retrieved facts` / `not automatically a slow
model` (the two completions).

What the second half is really guarding is visible in the TS trace's Map. The
translated Vercel span keeps its 19 `ai.*` **metadata** keys and has lost every
content-bearing one:

```
chat gpt-4o-mini (translated) → ai.model.id, ai.model.provider, ai.operationId,
  ai.request.headers.user-agent, ai.response.finishReason, ai.response.id,
  ai.response.model, ai.response.providerMetadata, ai.response.timestamp,
  ai.settings.maxRetries, ai.usage.* (9), operation.name,
  gen_ai.{system,request.model,response.model,response.id,
          usage.input_tokens,usage.output_tokens,response.finish_reasons}
```

and the outer `ai.generateText` span — the one that carried the full input under
`ai.prompt` before D92 — now carries 17 keys, none of them content. Metadata
stayed, which is the ruling: a translation that left the source copy behind
would be a copy, not a translation.

## 3. Rendering through the shipped query layer (D84)

`deploy/compose/sdk-checks.ts` asserts through `apps/web/src/server/data.ts` —
the same D17 facade the product renders from, in `OBSTACK_DATA_MODE=live`
against the read-only `obstack_web` user. It imports `REQUIRED_LAYERS` from
`trace-checks.ts` so the cross-layer claim has one definition across smoke, the
Helm acceptance and this harness; `trace-checks.ts` itself is untouched.

```
sdk-sample-py · POST /chat · 10.33ms · 7 spans (api=1 agent=1 tool=1 llm=1)
  llm gpt-4o-mini · 66+29 tokens · prompt 332B · completion 116B
  $0.000027 · 3 correlated log(s)
sdk-sample-ts · POST · 31.57ms · 6 spans (api=1 agent=1 tool=1 llm=2)
  llm gpt-4o-mini · 66+45 tokens · prompt 350B · completion 178B
  llm gpt-4o-mini · 64+45 tokens · prompt 314B · completion 178B
  $0.000073 · 0 correlated log(s) (not required — D84)
```

Every `llm` span is checked, not the first one — a `find()` would have passed
while one of the two JS mechanisms shipped an empty prompt. The trace must both
`getTrace()` **and** appear in `searchTraces()` with a root service and a
matching span count, so a row that exists but does not list is a failure.

Costs are ingest's, computed from the tokens and model the SDKs report (D9 — the
SDKs carry no pricing logic at all), which is exactly why a non-zero cost is
worth asserting from the SDK side.

`problemsWith` is `sdk-checks.ts`'s own, not `trace-checks.ts`'s: that
predicate demands a correlated log on every trace, and obstack-js ships no
logging-framework bridge this sprint. Correlated logs are asserted where they
are real — 3 of them on the Python sample, from the root-logger handler `init()`
installs — and not demanded where nobody built them (D84).

## 4. "Standard OTLP on the wire, verifiable by pointing them at any OTLP endpoint"

The clause, taken literally. Each sample is started once more with one variable
different — `OTEL_EXPORTER_OTLP_ENDPOINT` pointed at a stock
`otel/opentelemetry-collector-k8s:0.158.0` (the tag the repo already runs)
configured from a file written fresh for this leg: OTLP in, file exporter out,
nothing under `deploy/collector/` read. The assertion is made on what that
foreign process wrote down.

| claim | py | ts |
|---|---|---|
| the collector received spans over standard OTLP and wrote them out | pass | pass |
| its output carries `agent.answer_question`, `tool.knowledge_lookup`, `chat gpt-4o-mini` | pass | pass |
| and `gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.prompt`, `gen_ai.completion` | pass | pass |

`gen_ai.prompt` and `gen_ai.completion` appear here and nowhere in ClickHouse's
attributes Map, and both facts are correct: the SDK puts them on the wire as
span attributes, and **ingest** is what moves them into the dedicated columns.
That contrast is the clearest statement of where the perimeter is.

The "received it" check is on `"resourceSpans"` in the dump rather than a
non-empty file: the collector's logs pipeline writes to the same file and the
Python sample emits logs, so a file holding only log records would otherwise
have read as "the trace arrived".

## 5. Fail open, live (PRD §9 / D83)

Each sample is started with the endpoint on a dead port (`http://127.0.0.1:9`) —
the assembled whole, `init()` through instrumentations through batch processors
through exporter, not a unit test of a `catch`.

| claim | py | ts |
|---|---|---|
| the app starts at all | pass | pass |
| `POST /chat` still answers **200** with its real answer | pass | pass |
| and none of that run's telemetry reached ClickHouse | pass | pass |

The third row is the control that keeps the leg from describing an ordinary run:
the agent-trace count for the service is taken before and after, and the
container is stopped first, because both SDKs flush on shutdown — anything that
could still land has by then. The compose services carry
`stop_grace_period: 20s` for that stop: with a dead endpoint the Python
exporter spends ~9s retrying inside shutdown (measured, T4), and docker's 10s
default would put SIGKILL in the same second as the flush, making the leg's own
teardown a coin flip.

## 6. Contract pinning: `sdk_contract_test.go` (D81/D86)

The D8 names are now spelled in three languages. The new
`services/ingest/internal/mapping/sdk_contract_test.go` — the single sanctioned
test-only touch inside `services/ingest/**` — reads `mapping.go`'s `attr*`
constants by AST walk and both SDK modules
(`packages/obstack-py/src/obstack/attributes.py`,
`packages/obstack-js/src/attributes.ts`) by regex, and compares them. It runs in
the every-PR `go` job. Nothing is restated except `sdkAttributeDuties`, the one
fact no parser can derive: which of ingest's attributes are an SDK's to emit.

Proven red-capable, not merely green (S2.0 L1). Three falsifications, each
reverted to a byte-identical file immediately after:

| falsification | result |
|---|---|
| a declared literal drifts (`gen_ai.usage.input_tokens` → `…usege…`) | **red**, both directions: "does not declare `gen_ai.usage.input_tokens`, which mapping.go reads" *and* "declares `gen_ai.usege.input_tokens` … mapping.go reads no such attribute" |
| a duty entry names a constant `mapping.go` no longer has | **red**: "classifies attrProbeUnknownConstant, which no longer exists in mapping.go — the duty it described is now unenforced" |
| a real duty entry is deleted | **red**: "attrGenAICompletion = \"gen_ai.completion\" is new in mapping.go and unclassified in sdkAttributeDuties" |

The file also refuses to pass vacuously: an empty constant set, an empty owed
set, an unparseable SDK module and a duplicate declaration are all `t.Fatalf`,
because a contract test that compares two empty sets is worse than no test.

D86's other half — attributes module ↔ emitted span — is each SDK's own
conformance suite, where the literals are restated independently on the test
side. The drift chain closes in two links.

Full suite, per the repo runbook, with the compose ClickHouse up:

```

go vet ./...          → clean
go test -v -count=1 ./...  → ok, 129 PASS, 0 SKIP
```

## 11. Harness honesty (S2.3 L4)

The script destroys the compose volumes first, then **refuses to start** rather
than clean up when it finds anything it does not own: a container of the compose
project still standing under another profile, anything answering on one of the
six ports it uses, or a leftover probe-container name. The ownership check is
listed with every profile enabled on purpose — the narrow `--profile sdk` view
cannot see the containers that are the problem, and the first run of this script
duly printed a foreign `demo` container inside its own "the stack booted" line.

Two related defects found and fixed in the same place, both of the kind S2.3 L4
names: `docker compose run` failures were discarded to `/dev/null`, so a leg
that never managed to create its container reported the resulting silence as an
SDK failure; and "the collector received the trace" was a non-empty-file check
that a logs-only dump would satisfy. Infrastructure that cannot run is now a
loud refusal, not a failed claim about the SDKs.
