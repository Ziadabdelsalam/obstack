## 1. FINAL GOAL VISION — M3

M3 is done when obstack stops being a single-tenant pipeline with a demo workspace baked into an environment variable and becomes a product a stranger can buy their way into alone: Postgres arrives beside the telemetry flow and carries the identity the ClickHouse path never had — accounts, orgs and workspaces, invites, API keys whose wire format is byte-identical to the M1 dev keys with only the lookup moved from env to a table — so that a person who has never spoken to the builder signs up, is handed their own workspace and their own key, follows a three-tab quickstart that names the packages that actually exist, watches a "waiting for data…" screen flip to *their* first four-layer correlated trace, and finds a Connections hub whose cards open real connect flows and whose connected sources report live health from real ingest counters; usage meters against a plan, Stripe carries the money, exceeding quota degrades to sampled ingestion behind an honest banner rather than a hard cut, per-workspace pricing overrides and the workspace's own ingest-error count are visible in a settings surface that finally shows the user's own data instead of `Loopwork`, saved views follow the workspace instead of the browser, and clicking Explain on a failed trace returns a real root-cause summary assembled from that trace's own spans and correlated logs — with every surface a signed-up stranger can reach either telling the truth about their data or plainly labelled as sample content.

## 3. M3 sprint-level split — ALL options

The split is **ADVISOR-OWNED** (packet item 1). The record states it two incompatible ways, exactly as it did for M2:

- **D20** (`vision doc` §Questions item 4): presumptive seams **M3a = auth/workspaces/DB-backed keys + onboarding**, **M3b = billing/metering + Connections hub + Explain** — two sprints. D20's own text makes these presumptive, "to be confirmed or corrected at each phase's planning moment".
- **The S3 paragraph** (`vision doc` line 54): "Expected to exceed one team run; splits into sequential sprints (**identity+keys+settings, metering+billing, onboarding+connections, explain**) at planning time" — four sprints.

Both are written out below with a third (PM recommendation). Every option satisfies D20's fixed constraint: each sprint ends on a working, demoable product. Sprint IDs are provisional until the advisor rules.

**Common to every option — the foundation problem, stated once.** Two facts make the first sprint of every option structurally different from every sprint M1 or M2 ran:

1. **Postgres does not exist anywhere in this repo.** `apps/web/package.json:13-21` has no Postgres driver, no auth library and no Stripe SDK. `deploy/compose/docker-compose.yml` defines `clickhouse`, `ingest`, `demo` (profile `demo`), `sdk-sample-py`/`sdk-sample-ts` (profile `sdk`) and `collector` (profile `collector`) — no `postgres`. `deploy/helm/obstack/values.yaml:1-5` states the chart's scope as "M2 scope only (D35): CI-grade ClickHouse, ingest, the obstack-collector DaemonSet and the demo app".
2. **The workspace is a module-load constant, not a request value.** `apps/web/src/server/clickhouse.ts:12` — `export const workspaceId = process.env.OBSTACK_WORKSPACE_ID ?? "ws_demo";` — and every telemetry query binds it (`queries/traces.ts:330,336,369`, `queries/logs.ts:239,252`, `queries/overview.ts:166,172`). Ingest resolves its workspace from an env-parsed key map (`internal/config/config.go:104-121`, `internal/auth/auth.go:29-48`). Multi-tenancy is not a feature added beside this; it is a change to how every read in the product is scoped.

Whichever option is ruled, the sprint that lands (1) and (2) is the sprint everything else in M3 depends on, and it is the one that must not overrun.
