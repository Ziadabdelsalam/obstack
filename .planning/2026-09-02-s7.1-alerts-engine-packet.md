## 0. Frozen product contract (stated first — the engine exists to serve it)

What `/app/alerts` renders (from the mock, kept): a rules list (name, human-readable condition, channel name, enabled, last-triggered) and an events feed (severity, title, detail, time, link). What the mock implies and v1 KEEPS: rules are per-workspace objects; events are produced by evaluation, not hand-entered; events link into the product. What v1 FENCES OUT, absent-not-faked (D13): `AlertRule.actions` (one-click remediations — remediation is no milestone's yet), anomaly/spike/cluster events (the mock's token-spend and tool-failure-cluster events are Phase-2 vision; v1 events come only from rule evaluation). `runbook` stays (a free-text URL field, rendered as a link — cheap and honest).

**Query/mutation contract (freezes at kickoff, `lib/alert-types.ts`, client-safe, no imports — the metrics-types pattern):**
- `listAlertRules(ws)` → rows of `{ id, name, condition: AlertCondition, severity, channelId, channelName, enabled, runbook, state: "ok"|"firing", lastTriggeredAt: string|null }`
- `listAlertEvents(ws, limit)` → newest-first `{ id, ruleId, ruleName, severity, title, detail, link: string|null, delivery: "pending"|"delivered"|"failed", at }`
- `listNotificationChannels(ws)` → `{ id, name, kind, targetMasked, enabled }` — the target is ALWAYS masked on read (§Q3 secret rule)
- mutations (server actions, expose-mutations-only per S6.3-L2, lock-first per D429 pattern): create/update/enable/disable/delete rule; create/enable/disable/delete channel (delete REFUSED while a rule references it); `sendTestNotification(channelId)`.
- The human-readable condition string is RENDERED from the structured condition by one shared formatter — never stored, never parsed. Mock fixtures untouched, mock byte-identity per D114.

## 1. Q1 — Where the engine lives, and how N replicas stay correct

- **D477 — the evaluator is a ticker loop in the ingest binary** (house pattern: retention's sweep + metering's flush; wired in `main.go` with the same ordered shutdown — stop claiming before the pool closes). No new service, no new subcommand for serving; the drive and Go tests exercise an exported `EvaluateDue(ctx)` directly.
- **D478 — replica correctness by claim, not leader.** Each tick claims due rules with `SELECT … WHERE enabled AND next_eval_at <= now() FOR UPDATE SKIP LOCKED`, evaluates the claimed set, writes state/events inside the same transaction, then sets `next_eval_at`. N replicas never double-evaluate a rule by construction (no lease, no watermark — the metering §doc's spirit). Notification delivery happens AFTER commit (§Q3); a crash between commit and delivery is the at-least-once seam, resolved by the event's `delivery` column, not by re-evaluation.
- **D479 — cadence is one constant, 60s, for every workspace.** The phase-plan fence ("fixed per plan tier, not per rule") is read at its minimal point: rules never choose cadence, and v1 ships one number. Per-tier cadence is a pricing decision, pre-registered USER-VISIBLE for a billing revisit (the D365 shape) — it never lands silently.
- **D480 — evaluation fail-open posture.** A ClickHouse error or timeout (per-eval statement timeout, small) leaves the rule's state UNCHANGED and `next_eval_at` advanced — no event, no flap, one ops-side counter (`alert_evals_failed_total`). A rule that cannot be evaluated is not a firing rule; inventing severity from an outage would be a D13 violation aimed at the user's pager.

## 2. Q2 — Condition representation (structured, two source kinds)

- **D481 — `condition` is structured JSONB; the string is presentation.** Two shapes, discriminated on `source`:
  - `{ source: "metric", metric, type: "gauge"|"sum"|"histogram", agg, window, op: ">"|"<", threshold: number, filters: Record<string,string> }` — vocabulary IS the D363 contract: `type`+`agg` validity is `VALID_AGGS` verbatim (one table, no fourth copy — D390 held), `filters` the observed-attr-key shape. Evaluation = the aggregate over the window compared to the threshold.
  - `{ source: "trace", signal: "error_rate_pct"|"p95_ms", service: string|null, window, op, threshold }` — over `trace_summaries` with the house combinators (-Merge, never FINAL, never bare SELECT — the S6.1 rule binds the Go side too). Covers the mock's headline rules (error rate, p95) honestly; the pod-crash-loop rule is a `metric` condition over the S6.4 k8s leg.
- **D482 — window vocabulary is NEW and small: `"5m" | "15m" | "30m" | "1h"`.** `MetricRange` (1h/6h/24h) is a chart-width vocabulary, wrong for alerting; its "extensible at M6" hook is exercised by NOT overloading it. Windows ≤ 1h read the raw/1m tier — the rollup grain already serves this by construction.
- **D483 — cross-language parity is a proven artifact.** The condition schema exists twice (TS type in `lib/alert-types.ts`, Go struct in the evaluator) and is frozen by a shared fixture file of valid + invalid conditions that BOTH sides must accept/reject identically (the D385 precedent). Web validates on write (a rule that Go cannot evaluate must be unwritable); Go re-validates on claim and treats a failed parse as an eval failure (D480 path), never a crash.

## 3. Q3 — State machine, delivery semantics, egress security

- **D484 — per-rule state is `ok | firing`, transitions are the only event producers.** `ok→firing` emits an event at the RULE's severity (severity moves from the mock's per-event field to a per-rule field — the rule author decides how loud). `firing→ok` emits an `info` resolution event. While firing: silence — re-notify policy v1 = none, pre-registered as a rule-level option for a later run. No flap damping beyond what the window already provides.
- **D485 — delivery is at-least-once with a bounded, in-process retry.** Events row-persist as `pending` in the eval transaction; a post-commit deliverer POSTs to the channel (timeout 5s, 3 attempts, exponential backoff) then marks `delivered` or `failed`. `failed` is rendered honestly in the feed (the D13 answer to a dead webhook). No outbox daemon, no queue — a crash loses at most one delivery attempt round, and the `pending` row is visible truth. Redelivery of stuck `pending`/`failed` events is pre-registered, not built.
- **D486 — channel kinds v1: `webhook` and `slack_webhook`** (phase-plan fence). Both are one HTTPS POST; `slack_webhook` shapes the payload (`{text}` with title/detail/link). The generic payload is a versioned JSON document (`{version: 1, rule, event, workspace}`) — additive evolution only.
- **D487 — egress is a new capability class; the fences are code, not review notes.** The deliverer dials with a resolver-pinned client that REFUSES: non-HTTPS schemes, literal IPs, and any resolved address in private/link-local/loopback/metadata ranges — checked at dial time post-DNS (rebinding-proof), not by URL inspection. Response bodies are capped and discarded. Per-workspace delivery rate cap (constant, ops-counter on breach). Channel targets are secrets by default (a Slack webhook URL IS its own credential): stored plaintext in Postgres v1 (the api_keys posture precedent), NEVER returned whole by any read path — masked to scheme+host+last-4 — and never logged. At-rest encryption is pre-registered for the security milestone.
- **D488 — the test-notification path is the notifier's front door, not a bypass.** `sendTestNotification` walks the full deliverer (fences, retry, masking) and reports the real outcome — it exists so the drive and the user can prove a channel without waiting for a threshold to trip.

## 4. Q4 — DDL (`pgmigrations/0010_alerts.sql`, Postgres track, 0009 house style)

Three tables, all `workspace_id` FK → workspaces ON DELETE CASCADE, TEXT pks, CHECK never enum, timestamps as 0009:

- **`notification_channels`**: id, workspace_id, name (UNIQUE per ws, `<> ''`), kind CHECK IN ('webhook','slack_webhook'), target TEXT NOT NULL, enabled BOOL, created/updated. Deleting a channel referenced by a rule is REFUSED at the action layer AND by `alert_rules.channel_id` FK **ON DELETE RESTRICT** — refuse-never-cascade for cross-references (cascade would silently disarm rules).
- **`alert_rules`**: id, workspace_id, name (UNIQUE per ws), condition JSONB CHECK (`jsonb_typeof = 'object'`), severity CHECK IN ('critical','warning','info'), channel_id FK RESTRICT, enabled BOOL, runbook TEXT NULL, state CHECK IN ('ok','firing') DEFAULT 'ok', last_triggered_at TIMESTAMPTZ NULL, next_eval_at TIMESTAMPTZ NOT NULL DEFAULT now(), created/updated. Index `(next_eval_at) WHERE enabled` — the claim query's shape.
- **`alert_events`**: id, workspace_id, rule_id FK → alert_rules ON DELETE CASCADE, severity CHECK, title, detail, link TEXT NULL, delivery CHECK IN ('pending','delivered','failed') DEFAULT 'pending', created_at. Index `(workspace_id, created_at DESC)`.
- **D489 — event retention rides the existing sweeper.** `retention.go` gains `alert_events` in its per-workspace plan-window sweep (the 0004 pattern extended in place, not a second mechanism). No per-workspace count cap in v1; the rate-of-production bound is D479's cadence × rule count, and a rule-count-per-workspace cap (constant, generous) closes the abuse hole.
- **Tenancy (D7/D11, binding):** every web read/mutation through the workspace-scoped module; the evaluator's ClickHouse queries are `workspace_id`-first with the scoping proven red per new read path (metric + trace legs separately); the claim query is workspace-blind BY DESIGN (it schedules, it does not read telemetry) — stated so no reviewer "fixes" it.
