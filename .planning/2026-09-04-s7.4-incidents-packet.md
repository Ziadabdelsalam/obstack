## 2. Q2 — The object: DDL, vocabularies, promotion, retention, bound

- **D524 — `services/ingest/pgmigrations/0013_incidents.sql`, ONE table, no `ALTER`, 0012 house style.** `id TEXT PRIMARY KEY` (`inc_` + 16 hex, the `rule_`/`chan_`/`evt_`/`slo_`/`chg_` idiom), `workspace_id TEXT NOT NULL REFERENCES workspaces (id) ON DELETE CASCADE`, `title TEXT NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200)`, `status TEXT NOT NULL CHECK (status IN ('ongoing','resolved')) DEFAULT 'ongoing'`, `severity TEXT NOT NULL CHECK (severity IN ('critical','warning','info'))`, `origin TEXT NOT NULL CHECK (origin IN ('manual','alert')) DEFAULT 'manual'`, `impact TEXT NOT NULL DEFAULT '' CHECK (char_length(impact) <= 500)`, `summary TEXT NOT NULL DEFAULT '' CHECK (char_length(summary) <= 2000)`, `started_at TIMESTAMPTZ NOT NULL`, `ended_at TIMESTAMPTZ NULL`, `opened_from_event_id TEXT NULL REFERENCES alert_events (id) ON DELETE SET NULL`, `created_at`/`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` (set by hand — no trigger exists anywhere in the set). **There is NO `rca` column and no `rca_generated_at` (D555): the Explain rail does not store answers, and "rides the rail unchanged" is taken literally.** Table-level: `CHECK ((status = 'resolved') = (ended_at IS NOT NULL))` and `CHECK (ended_at IS NULL OR ended_at >= started_at)` — the both-or-neither idiom (`0011:42`, `0012:47`) makes "ongoing with an end" and "resolved with none" unrepresentable rather than merely unexpected. The time range is TWO columns because `window` is reserved (0012 ships `eval_window` and says why); there is no `duration` column — the mock's `"22m"` is a display string and a stored duration is a third copy of two columns that can disagree. Indexes: `incidents_workspace_id_started_at_idx ON (workspace_id, started_at DESC)` and a partial UNIQUE `incidents_opened_from_event_id_idx ON (opened_from_event_id) WHERE opened_from_event_id IS NOT NULL` — **single-column, deliberately dropping the `workspace_id` prefix every other per-workspace index leads with, because this index is also the FK's own `SET NULL` lookup** (the `alert_events_slo_id_idx … WHERE slo_id IS NOT NULL` / "the cascade's own lookup" precedent at `0012:65-66`); a `(workspace_id, …)` leading index cannot serve `WHERE opened_from_event_id = $1` and would make retention's 5000-row batches seq-scan `incidents` ⟨rev⟩. The DDL comment states that. **No `UNIQUE (workspace_id, title)`**, and the store therefore carries NO `refusingDuplicateName` and NO `23505` branch — stated in both files so nobody adds a dead one for house-style symmetry: two real outages share a title, and the promotion path copies the alert's title so a recurring rule mints the same string by construction. `0013` adds no constraint to an existing table, so it needs no `DO $$ … pg_constraint … regclass $$` guard; every CHECK is inline in a `CREATE TABLE IF NOT EXISTS` and a raw double-apply is a no-op by construction (the second pass prints one table NOTICE and two index NOTICEs — the PRIMARY KEY's implicit index is created inside the skipped table and emits nothing ⟨rev⟩). Pin: `qa_a6_migrations_test.go:178`'s `const want` gains `,0013_incidents`. That is the ONLY assertion the migration moves; four prose/test-name references to sibling versions exist and this sprint adds a fifth (the integration test's DSN guard, which must name `0013_incidents`).
- **D525 — the vocabularies.** Status is the mock's two and no more; `0002_saved_views.sql:10-12`'s rule (a CHECK is used precisely so widening later is an ordinary migration) makes the minimal true set correct, and a third state invented before a product need names it is inventing product. Severity is the **alert vocabulary verbatim, three members including `info`**, because severity is not invented here: it is copied from an `alert_events` row whose CHECK is `('critical','warning','info')`, and any narrower target forces a mapping that overstates an info event or understates a critical one (D13 forbids both). The action is the whole ruling: NO ACTION (the Postgres default) and RESTRICT both raise 23503 against `retention.go:162-163`'s ctid batch DELETE and **wedge that workspace's sweep forever** (the sweeper logs, counts `sweepFailures`, skips the table and retries the identical failing statement every interval); CASCADE deletes an operator's postmortem because their alert aged out. ## 3. Q3 — The stitched timeline: which sources, which SQL, what is honestly absent

- **D530 — three legs, read at render time, no link table and no materialization.** The run-goal says the timeline is "stitched by window-join", which is a read-time join; a link table would only be for operator-curated attach/detach, which the fence does not name, and it would need its own FK action, index and retention answer. `alert_events` (Postgres, on `created_at`), `change_events` (Postgres, on `at` — the event's OWN time, never `created_at`, the rule `changes.ts` states in its header), and `obstack.spans` (ClickHouse). Both Postgres legs already have covering indexes and need no new ones (`alert_events (workspace_id, created_at DESC)`, `change_events (workspace_id, at DESC)`). Each read lives in the module that owns its table — a second module selecting from `alert_events` would put two owners on one table's read shapes — so `server/alerts.ts` gains `listAlertEventsInWindow` and `server/changes.ts` gains `listChangeEventsInWindow`, both reads, both passing their limit through the existing `clampLimit` ⟨rev⟩; `changes.ts` stays reads-only and its `changes.test.ts:41` `seen.length === 2` pin moves to 3 with the third read exercised.
- **D531 — the trace leg reads `obstack.spans`, not `trace_summaries`.** `obstack.spans` is `PARTITION BY toDate(start_time)` (`0001_spans.sql:44`), so a two-sided `start_time` bound is a genuine partition prune. `obstack.trace_summaries` has NO `PARTITION BY` (`0003:40-41`) — its `max_seen_date >= …` filter is a cheap Date column filter that the repo's own comments loosely call a "partition prune", and for a bounded historical window that is exactly backwards; worse, `eval_slo.go` bounds the merged `min(min_start)`, i.e. the trace's START, so a trace that began before the incident and errored twelve minutes into it is invisible to that shape — and that erroring span's instant is precisely what a timeline row must be drawn at. The read is the `issues.ts:106-114` shape with a second bound added:
  ```sql
  SELECT service, name AS span_name, toUInt32(count()) AS errors,
         toUInt32(min(toUnixTimestamp(start_time))) AS first_seen_epoch_s,
         toUInt32(max(toUnixTimestamp(start_time))) AS last_seen_epoch_s,
         argMin(trace_id, start_time)                AS example_trace_id
    FROM obstack.spans
   WHERE workspace_id = {workspace_id:String} AND status_code = 'error' AND trace_id != ''
     AND start_time >= fromUnixTimestamp({since_s:UInt32})
     AND start_time <  fromUnixTimestamp({until_s:UInt32})
   GROUP BY service, span_name
   ORDER BY first_seen_epoch_s, service, span_name
   LIMIT {fetch:UInt32}
  ```
  `{workspace_id:` is literally present (`runScoped`'s text tripwire refuses SQL without it). `trace_id != ''` is load-bearing: the summaries MV has no write-side trace-id filter and `trace_id = ''` rows legally exist, so without it `argMin` can return `''` and the entry links at the traces LIST. `argMin`, not `argMax`: the entry is drawn at `first_seen`, so an `argMax` example would link a trace that ran twenty minutes after the moment the row sits at. `ORDER BY first_seen`, not by count: a cap on a ranked list deletes the quiet tail, but a cap on a chronological one deletes only the tail, which is the only truncation a timeline survives.
- **D532 — the entry states its own grain, and never draws a whole-window aggregate at a point instant ⟨rev⟩.** The entry carries both `at` (= `first_seen`) and `until` (= `last_seen`); the TITLE names the span (`POST /chat on agent-worker`), and the count with its span rides the DETAIL line (`2 errors, 13:04 → 13:19`). A title reading "2 errors on POST /chat" drawn at 13:04 states a number not reached until 13:19.
