## 0. What the chart gives the pilot today, and what it does not

**Ships (0.6.0):** ClickHouse and Postgres as StatefulSets on PVCs (`clickhouse.storage.size: 20Gi`, `postgres.storage.size: 10Gi`, `storageClassName` empty = the cluster's default class); the ingest Deployment (`replicaCount: 2`, `OBSTACK_MIGRATE_ON_BOOT=false`) plus one migrate Job per store rendered as `pre-upgrade` hooks; the `web` Deployment + ClusterIP Service running the live-stamped image; the `obstack-collector` DaemonSet (pod logs, kubelet metrics) and the single-replica cluster collector (events + cluster metrics, `collector.cluster.enabled`); a demo pod; one chart-owned Secret with an `existingSecret` override per credential group and FIXED key names (`clickhouse-ingest-password`, `clickhouse-web-password`, `postgres-password`, `better-auth-secret`, `explain-api-key`, `vercel-drain-secret` — README "Credentials and rotation"); optional Ingress for web and for ingest's OTLP/**HTTP** surface (gRPC deliberately not exposed; enabling ingest's sets `OBSTACK_PUBLIC_OTLP_HTTP_ENDPOINT` on web so the quickstart renders it); requests+limits on ingest, web, both collectors and the demo, **requests only** on the two stores (D283). Measured on CI's 2-vCPU kind node the defaults request **990m** against a **1000m** budget (README "The node's CPU-request budget"; `acceptance.ts budget` is the guard).

**Does not ship, by ruling, and the pilot must supply or accept:** an ingress controller and certificates; backups; HA of anything; a pull secret (no `imagePullSecrets` anywhere in the nine pod templates — measured); a way to switch Explain out of `fake` mode (the web Deployment carries `OBSTACK_EXPLAIN_API_KEY` from the Secret but no `OBSTACK_EXPLAIN_MODE`, so Explain and incident RCA answer with the fake provider on Kubernetes today — `values.yaml:141`'s own comment names the variable the chart never sets); a `demo.enabled` toggle (the demo pod always renders — measured, no `.Values.demo.enabled` in any template); the collector's key from a Secret (`collector.apiKey` is a VALUES LITERAL rendered as `value:` into both collector workloads, `templates/collector/daemonset.yaml:53-54`, `cluster-deployment.yaml:71-72`); an operator path to put a self-hosted workspace on a plan other than `free`.

## 1. Q1 — The cluster and the VM

- **D680 — one VM, one node, k3s.** The chart assumes a default StorageClass that provisions dynamically ("the shape a fresh kind cluster … and most real clusters both satisfy", `values.yaml` at `clickhouse.storage.storageClassName`) and an ingress controller already in the cluster (D253). k3s gives both out of the box — `local-path` as the default class and Traefik as the ingress controller — plus a service LB, in one binary the client's VM can run unattended. **To verify on the VM before the install, not assume:** `kubectl get storageclass` shows `local-path (default)`; `kubectl get ingressclass` shows `traefik`; the node's allocatable CPU/memory (`kubectl describe node`) against §1 D681. kind stays what it is — the CI/acceptance harness, never a production host. **Alternative:** a managed control plane the client already pays for; nothing in the chart cares, and the two verifications above are the same.
- **D681 — the sizing floor is stated as requests plus measured headroom, and it is a floor to be MEASURED on the client's traffic, not a spec.** The chart's own requests sum to ≈990m CPU and ≈1.8 GiB memory (ClickHouse 1Gi, Postgres 128Mi, ingest 2×128Mi, web 256Mi, collector 64Mi/node, cluster collector 64Mi, demo 64Mi); k3s's own control plane on the same node needs its share; and ClickHouse's real working set grows with retained data and has NO limit by ruling (D283 — "a wrong limit OOM-kills the store it was meant to protect"). The floor for the pilot: **4 vCPU / 8 GiB / 60 GiB disk**, with the PVC sizes set from the client's expected event volume and plan retention (§6), and `acceptance.ts budget` run against the pilot's values file BEFORE the VM sees it (README: "a pod that cannot be scheduled never starts, never fails, and never times out on its own — `helm install --wait` simply sits on it"). Flagged (g).
- **D682 — the VM is amd64, and every image is CI's.** The published images are single-manifest (measured: the web manifest is not an index), built on `ubuntu-latest`, i.e. `linux/amd64`. A laptop build on this Mac is `arm64` and will not start on the VM; `kind load`-style side-loading has no place in the pilot. The chart's `*.image` values point at `ghcr.io/ziadabdelsalam/<name>:<tag>@sha256:<digest>` (digest from the `publish` job's step summary, "Record published digests"), with `pullPolicy: IfNotPresent`.

## 2. Q2 — Images: the pull that fails today, and the two ways out

- **D683 — the packages are private although the repository is public (measured: anonymous manifest GET → HTTP 403 for all three at the merge sha), so a client cluster cannot pull them as the chart stands.** GitHub package visibility does not follow the repository's; each container package has its own setting. **As drafted:** make the four packages (`obstack-web`, `obstack-ingest`, `obstack-clickhouse`, and `obstack-demo-agent` if it is ever published) PUBLIC — the source they are built from is already public, the mode stamp and the refusal matrix are proven on every publish (`images.yml`), and a public image carries no credential (the chart's Secret does). Flagged (a). **Alternative:** the chart gains `global.imagePullSecrets` (a list rendered into all nine pod templates — 0.7.0, additive), and the pilot creates a `kubernetes.io/dockerconfigjson` Secret from a fine-grained PAT with `read:packages` on the client cluster — a credential of the user's on the client's machine, rotating on the user's schedule, which is exactly the class D253 kept out of the chart.
- **D684 — the tag is the merge sha, pinned by digest, and the pilot never floats.** `images.yml` publishes `sha-<sha>` only ("no `latest`, no `master`" — its own comment), and the D14 rule for the chart is exact pins. The pilot's values file names the sha AND the digest; an upgrade is a new values file, reviewed like any other change.

## 3. Q3 — The values file (its shape; no literal ever lives in the repo)

- **D685 — credentials come from four brought Secrets, never from `--set`.** `clickhouse.existingSecret`, `postgres.existingSecret`, `web.existingSecret`, `ingest.existingSecret`, each with the README's fixed key names; `web.betterAuthSecret` stays empty in the file (its value lives in the web Secret's `better-auth-secret`), generated once with `openssl rand -base64 32` on the VM. Rotation follows README "Credentials and rotation" verbatim — the ClickHouse rotation is a Secret update plus `kubectl rollout restart` of the StatefulSet AND the ingest Deployment; the Postgres password is initdb-time only (README "Postgres in this chart").
- **D686 — the two origins.** `web.betterAuthUrl: https://obstack.<client-domain>` (D119: the `https://` origin is what upgrades the session cookie to `__Secure-`; a wrong value here is a login that never sticks) and `web.ingress.enabled: true`, `host`, `className: traefik`, `tls.enabled: true`, `tls.secretName` (§4). `ingest.ingress.enabled: true`, `host: otlp.<client-domain>` — HTTP OTLP only, for senders OUTSIDE the cluster (a developer laptop, a CI job posting a change event); the client's own pods send in-cluster to `http://<release>-ingest.<namespace>.svc:4318` (or `:4317` gRPC, which the Ingress does not carry and does not need to).
- **D687 — the collector's key is issued, not seeded, and that makes the install two-step.** `collector.apiKey` defaults to `ok_dev_local`; a real deployment "supplies a key issued in settings through a Helm values file or a mounted secret" (`deploy/collector/README.md`, "Bearer key"). There is no key before there is a workspace, and no workspace before the product is up and someone signs up: **install → sign up → Settings → API keys → issue an `ingest` key → `helm upgrade` with it.** The value today is a literal rendered into the pod spec; the 0.7.0 item is a `collector.existingSecret` with a `collector-api-key` key (the chart's own pattern), so the key never passes through the values file either. Until then the pilot's values file is itself a secret and is handled as one.
- **D688 — the demo pod is off, and the chart needs the switch.** The demo pod exists for the acceptance rider (a second uninstrumented container as the NEARBY log source, D37.2) and sends under the seeded dev key. On the client's cluster it is noise, a CPU request, and a writer into `ws_demo`. 0.7.0 adds `demo.enabled` (default `true`, so kind and CI render exactly what they render today); the pilot sets `false`. Until it exists, the pilot's proof (§11) keeps the demo pod for the four-layer assertion and disables it by `helm upgrade` right after. Flagged (f).
- **D689 — storage from retention, not from the default.** `clickhouse.storage.size` and `postgres.storage.size` are set from the client's expected events per day × plan retention (§6) with headroom; `local-path` volumes are directories on the VM's disk, so the disk itself is the ceiling (§1 D681's 60 GiB is the floor for that reason).

## 4. Q4 — Ingress and TLS

- **D690 — Traefik terminates TLS; the certificate is a Secret the chart never renders.** `web.ingress.tls.secretName` and `ingest.ingress.tls.secretName` name an existing `kubernetes.io/tls` Secret ("this chart never issues or renders certificate material", `values.yaml` at `web.ingress.tls`). **As drafted:** cert-manager with a Let's Encrypt `ClusterIssuer` (HTTP-01 — needs port 80 reachable on the VM for the challenge) issuing both hosts, the standard k3s+Traefik pairing. **Alternative:** the client's own certificate (a wildcard they already hold) loaded as the Secret, renewed by them — zero new components, one more thing on their calendar. Flagged (d).
- **D691 — `/mcp` rides the web Ingress; the chart's one addition is the address the product prints.** The S8.1 endpoint is a path on the web Service (S8.1 packet D640); `pathType: Prefix` on `/` (`templates/ingress/web.yaml`) already carries it. What the chart adds (0.7.0, §12) is `OBSTACK_PUBLIC_MCP_ENDPOINT=https://<web.ingress.host>/mcp` on the web Deployment under the existing `web.ingress.enabled` branch — the same D277 shape that already renders `OBSTACK_PUBLIC_OTLP_HTTP_ENDPOINT` from the ingest Ingress (`templates/web/deployment.yaml:112`) — so `/app/mcp` prints the client's real address (S8.1 D653). A developer's Claude Code reaches `https://obstack.<client-domain>/mcp`; nothing is exposed that the product itself does not already expose.

## 5. Q5 — Explain and RCA on the cluster

- **D692 — `web.explainMode` is the 0.7.0 value that makes Explain real on Kubernetes, and until it lands the pilot's Explain is honestly fake.** `apps/web/src/server/explain/client.ts` reads `OBSTACK_EXPLAIN_MODE` (default `fake`) and, in `anthropic` mode, the key from `OBSTACK_EXPLAIN_API_KEY` — which the chart already sources from the web Secret's optional `explain-api-key`. The client's Anthropic key goes into the web Secret, and Explain runs are metered per plan (`plans.explain_quota`: 20 on free, 200 on pro — §6 decides which).

## 6. Q6 — The plan a self-hosted workspace lands on, and why the pilot must move it

- **D693 — a fresh workspace is on `free`: 50,000 events per month and 7-day retention, with no billing rail to change it.** `0005_metering.sql:128-129` seeds `free (50000, 7 days, $0)` and `pro (1000000, 30 days, $49)`; D163 makes "no `workspace_plans` row" mean `free`; `OBSTACK_BILLING_MODE` defaults to `fake` (`server/billing/client.ts:29`) and the chart sets nothing else, so the product's own upgrade path (Polar checkout) does not exist on the client's cluster — correctly: Polar is the hosted product's merchant of record (D110), not the client's. A pilot sending real traffic crosses 50,000 events in hours, and what follows is the S3.3 quota posture (head sampling, the degradation the product was built to apply) plus a 7-day sweep of everything it keeps — the pilot would be evaluating a throttled, short-memory obstack and would not know it.
- **D694 — the operator moves the workspace to `pro` by one row, documented as the pilot's step 4, and the product call is flagged.** `kubectl exec` into the Postgres pod, then `INSERT INTO workspace_plans (workspace_id, plan_id) VALUES ('<ws>', 'pro') ON CONFLICT (workspace_id) DO UPDATE SET plan_id = 'pro', updated_at = now();` — the workspace id is what the product's General tab prints. No code change; the row is the one authority everything reads (`usage.ts` D163's join). **Flagged (b), as a product decision this touchpoint may not take:** a self-hosted deployment has no reason to carry the hosted product's quota table at all, and the honest shapes are either a `self-hosted` plan row (unbounded events, retention as a chart value) seeded by a migration behind an operator flag, or the recipe above promoted to the self-hosting docs as the stated posture. Both change what a signed exit line says about plans; the packet drafts neither and asks.

## 7. Q7 — The seeded dev key on a cluster the internet can reach

- **D695 — `0004_api_keys.sql` seeds `ok_dev_local` for `ws_demo` in EVERY install, the docs call it "a public credential by design — it is printed in the repository", and on the client's cluster that is a write door with a published key.** `deploy/helm/obstack/README.md:430` and `docs/self-hosting/docker-compose:89-94` both state the seed; neither says what a real install does with it. Once ingest's Ingress is up (D686), anyone reading the public repository can POST telemetry into the client cluster's `ws_demo` — not the client's workspace, so not a read of their data, but a write into their ClickHouse, a quota sink and a log stream nobody asked for. **Pilot step, right after the sign-up:** revoke it — `UPDATE api_keys SET revoked_at = now() WHERE id = 'key_dev_local';` — which the demo pod and the default `collector.apiKey` both depend on, which is why D688's demo switch and D687's issued key come first in the order. **Flagged (c) as a product call:** a real install should not need a manual revocation of a migration's seed; the shapes are a chart value that revokes the seed after the pg-migrate Job (a second one-shot Job, the runner's pattern), or a migration that seeds it only under a dev/CI flag the compose and kind paths set. Not ruled here.

## 8. Q8 — Backups and upgrades

- **D696 — backups are OUT of the chart by ruling, so the pilot brings the smallest honest one.** `local-path` PVCs are directories under `/var/lib/rancher/k3s/storage` on the VM's disk; there are no volume snapshots on that class. **First cut, as drafted:** the VM's own disk snapshot on the client's hypervisor schedule (whole-node, consistent enough for a pilot, zero new components) PLUS a nightly `pg_dump` CronJob to an off-VM target — Postgres holds the identity, keys, incidents, alerts and dashboards, the rows a person authored and no machine can re-derive (the D528 argument). ClickHouse's `BACKUP DATABASE obstack TO Disk('backups', …)` needs a `backups` disk declared in the server config, which `files/` does not carry (users.xml only) — a 0.7.0 `config.d` item if the client wants store-level backups beyond the snapshot. Flagged (e).
- **D697 — upgrades are `helm upgrade --wait --timeout 300s` from a reviewed values file, and the migrate Jobs are the gate.** The Jobs render as `pre-upgrade` hooks (README "Why ClickHouse is a normal resource, and the migrate Job renders two ways"); the serving pods refuse to start on an unapplied set, so a forgotten migration crash-loops loudly instead of serving against a table missing columns. Exactly one migration runner per upgrade (compose README "Exactly one migration runner per upgrade") — the pilot never runs `ingest migrate` by hand beside the Job. A fresh install never meets the 0.2.0 boundary; the D276 guard is armed anyway.

## 9. Q9 — The client's application

- **D698 — two instrumentation paths, both already documented, and the pilot picks per service.** (1) An obstack SDK from source — the registries hold name-hold `0.0.1` placeholders (root README "Pre-release"), so `pip install ./packages/obstack-py[fastapi]` from a checkout, or `npm pack` of `packages/obstack-js` installed from the tarball — two lines and the `@trace_agent`/`@trace_tool` names. (2) Plain OpenTelemetry with `OTEL_EXPORTER_OTLP_ENDPOINT=http://<release>-ingest.<namespace>.svc:4318` and `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20<ingest key>` (the URL-encoded form the README shows; `demo/agent-app` is the running proof). The four layers (`api`, `agent`, `tool`, `llm`) appear the same way on either path.
- **D699 — the collector reads the client's pods without touching them.** The DaemonSet tails every pod's stdout on its node except `collector.excludeContainer` (pod identity stamped by the collector, D43, never trusted from the sender), ships kubelet metrics, and the cluster collector ships events and cluster state, so `/app/infra` and each trace's `k8sEvents` render for the client's namespaces with no change to their manifests. The RBAC both receivers need is the chart's ClusterRole (README "The cluster collector"). The client's namespaces are named nowhere: the collector is cluster-wide by design, and a client that wants a namespace fence gets it from a `filter` processor in `collector-config.yaml` — a 0.7.0 value if asked, not an assumption.

## 10. Q10 — Claude Code over MCP (lands with S8.1)

- **D700 — the developer's setup is one command, and the key is a read key.** After S8.1 ships in the web image the pilot upgrades to: Settings → API keys → issue a key with scope `read` (S8.1 D644), then on the developer's machine `claude mcp add --transport http obstack https://obstack.<client-domain>/mcp --header "Authorization: Bearer <read key>"` (the CLI's form as installed here; the product's `/app/mcp` page prints the exact line with the real origin, S8.1 D654). The tools are S8.1's twelve; nothing writes; the key can be revoked from the same tab. The cluster can be installed and instrumented BEFORE S8.1 lands — MCP arrives with an image upgrade, not a reinstall.

## 11. Q11 — The proof, in order

1. **`acceptance.ts budget`** against the pilot's values file, on the laptop — over budget for the VM's allocatable means the install would hang, not fail.
2. **`acceptance.sh` on a local kind** with the pilot's values (GHCR images, `pullPolicy: IfNotPresent`, both Ingresses off, demo on) — the chart's own signed proof, run once with the client's shape before the VM is touched.
3. **On the VM:** `helm install obstack deploy/helm/obstack -f pilot-values.yaml --timeout 900s --wait`; both migrate Jobs `Complete`; `https://obstack.<client-domain>/login` answers 200 over TLS; sign-up; the plan row (§6); the dev key revoked (§7); an ingest key issued and `helm upgrade` with it (§3 D687); the demo pod off (§3 D688).
4. **The exit:** the client's instrumented service handles one request and the trace resolves in `/app/traces/<id>` with its layers, spans, prompt/completion on the llm span, cost priced at ingest, and the collector's correlated logs (the smoke assertion, taken through the product instead of the harness). Then, after the S8.1 upgrade, `tools/list` and `get_trace(<that id>)` from a Claude Code session.
5. **Recorded:** the VM's measured footprint after 24h of the client's traffic (CPU, memory per pod, ClickHouse disk growth per day) — the numbers D283 pre-registered as "reopen-on-measurement", and the first ones a real install will ever produce.
