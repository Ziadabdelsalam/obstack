# Self-hosting with the Helm chart

The chart installs the obstack stack on Kubernetes: ClickHouse and Postgres as
StatefulSets with PersistentVolumeClaims, the ingest Deployment plus its two
migration Jobs, the web workload, the `obstack-collector` DaemonSet, and a demo
app pod.

{/* D450/D451/D465 */}

Since chart 0.6.0 the collector also reports the cluster it runs on: the
DaemonSet scrapes its own node's kubelet, and a single-replica cluster
collector (behind `collector.cluster.enabled`, default on — the same workload
that ships Kubernetes events) watches the API server, so `/app/infra` renders
the release's own nodes and pods with no extra configuration. The seventeen
metric names it is fenced to, the RBAC both receivers need and the per-node
series budget are in `deploy/collector/README.md` under "Kubernetes metrics".
0.6.0 is a **non-additive** bump: the old `k8sEvents` values block became
`collector.cluster.*` with deliberately no alias — a values file still setting
the old key is silently ignored and the collector comes up enabled — and the
singleton's objects renamed `<release>-collector-events` →
`<release>-collector-cluster`; the chart README's "Upgrading to 0.6.0" section
has both rules.

{/* 0.7.0 — the client-pilot bump, the pilot packet's §12 */}

Since chart 0.7.0 the chart is meant for a cluster that is not a throwaway:
the demo pod has a switch (`demo.enabled`), Explain's provider is stated in
the manifest (`web.explainMode`), the collector's key lives in a Secret
(`collector.existingSecret`), the web Ingress tells the product its `/mcp`
address, and an opt-in `backups` disk gives `BACKUP DATABASE` somewhere to
write. 0.7.0 is additive — a 0.6.0 values file renders a valid release, and
the web pod and both collector pods roll once on the upgrade. "A real install,
in order" below is the runbook that uses all of it.

## Install

The chart lives in this repository — there is no chart repository to add — and
runs from images this repository builds, so build and load them into the cluster
first.

```bash
helm install obstack deploy/helm/obstack --timeout 900s --wait \
  --set "web.betterAuthSecret=$(openssl rand -base64 32)"
```

`900s` is the migrate Job's own deadline, which already contains a cold
ClickHouse pull; a warm node is done in about 18 seconds.

`web.betterAuthSecret` is the one value with no default — a committed
cookie-signing secret in a distributable chart is a shipped vulnerability — and
it is not optional: a live-stamped web image booted without it refuses to serve,
so `--wait` would sit on a crash-looping pod until the timeout. Set
`web.betterAuthUrl` to the origin a browser reaches the deployment on.

Real deployments replace the local images with the published ones, pinned by
digest, and bring their own Secrets, origins and certificates — "A real
install, in order" below walks through it.

## What the chart does and does not cover

In scope, and shipped: ClickHouse and Postgres with durable storage, the ingest
Deployment and its migration Jobs, the web workload, the collector DaemonSet
and the cluster collector, a chart-owned Secret with an `existingSecret`
override on every credential (the collector's key included since 0.7.0),
optional Ingress for web and for ingest's OTLP/HTTP surface, CPU and memory
requests on every workload with limits everywhere but the two stores, a demo
pod with a switch, and an opt-in `backups` disk for ClickHouse.

Deliberately **not** in scope, and not a gap to fill quietly: HA beyond ingest's
existing replica story, autoscaling, PodDisruptionBudgets, NetworkPolicies,
multi-replica ClickHouse, backup automation, an ingress controller,
certificates, and a registry pull secret. Limits are **not** set on ClickHouse
or Postgres: sizing a database's limits is a measurement, not a guess, and a
wrong limit OOM-kills the store it was meant to protect.

`ingest.replicaCount` defaults to 2. Enabling ingest's Ingress exposes the
OTLP/HTTP surface and automatically sets `OBSTACK_PUBLIC_OTLP_HTTP_ENDPOINT` on
the web workload, so the product's quickstart renders that address; **gRPC is
deliberately not exposed**, and a deployment that publishes only HTTP gets an
honest omission in the quickstart rather than an address nothing serves. No
ingress controller and no cert-manager ship here — `web.ingress.enabled` and
`ingest.ingress.enabled` assume one already exists in the cluster.

## A real install, in order

The chart's own proof runs on a kind cluster with locally built images, a
seeded dev key and a demo pod. A cluster that carries real traffic differs in
every one of those, and this is the order that gets from an empty cluster to a
developer's coding agent reading a trace.

### 0. The cluster

One node is enough to start, and the chart assumes two things of it: a default
StorageClass that provisions dynamically, and an ingress controller already
installed — the chart ships neither, nor certificates, nor a registry pull
secret. k3s gives all of that in one binary (`local-path` as the default class,
Traefik as the controller); verify rather than assume:

```bash
kubectl get storageclass            # one marked (default)
kubectl get ingressclass            # traefik, or whatever you run
kubectl describe node | grep -A2 Allocatable
```

Size from the chart's requests plus headroom, then measure: the defaults
request just under one CPU and about 1.8 GiB of memory before ClickHouse's
working set grows with retained data (it has no limit, by design). Four vCPUs,
8 GiB and 60 GiB of disk is the floor for a pilot, and the disk is the ceiling
for `local-path` volumes, which are directories on it. Run the chart's own
budget check against your values file before the cluster ever sees it — an
unschedulable pod never fails, it holds the install's `--wait` until the
timeout:

```bash
npx tsx --tsconfig apps/web/tsconfig.json --conditions react-server \
  deploy/helm/obstack/acceptance.ts budget -f pilot-values.yaml
```

### 1. Images from the registry

Every merge to `master` publishes three images to GitHub's container registry,
tagged by commit and never floated: `ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>`
(the live-stamped build; a `mock-sha-` twin serves the public demo and refuses
to serve real stores), `ghcr.io/ziadabdelsalam/obstack-ingest:sha-<sha>` and
`ghcr.io/ziadabdelsalam/obstack-clickhouse:sha-<sha>` (the hosted product's
ClickHouse image — the chart pins the upstream `clickhouse.image` and does not
use it). The publish run's summary records each image's digest; pin both:

```yaml
web:
  image: ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>@sha256:<digest>
  pullPolicy: IfNotPresent
ingest:
  image: ghcr.io/ziadabdelsalam/obstack-ingest:sha-<sha>@sha256:<digest>
  pullPolicy: IfNotPresent
```

They are `linux/amd64`, built on GitHub's runners; a laptop build on Apple
silicon will not start on an amd64 node, and side-loading has no place outside
kind. The packages are private today — an anonymous pull is refused — so a
cluster outside this repository's owner pulls them only once they are made
public in the package settings, or with a registry pull secret of its own (the
chart renders no `imagePullSecrets`; that is deliberately the cluster's).

### 2. What you bring: Secrets, origins, storage

Credentials never pass through the values file. Create the Secrets first, with
the chart's fixed key names, and name them:

```bash
kubectl create secret generic obstack-stores \
  --from-literal=clickhouse-ingest-password="$(openssl rand -base64 24)" \
  --from-literal=clickhouse-web-password="$(openssl rand -base64 24)" \
  --from-literal=postgres-password="$(openssl rand -base64 24)"
kubectl create secret generic obstack-web \
  --from-literal=better-auth-secret="$(openssl rand -base64 32)" \
  --from-literal=explain-api-key="<your Anthropic key, or omit the line>"
```

```yaml
clickhouse:
  existingSecret: obstack-stores
  storage:
    size: 100Gi           # events per day × retention, with headroom
postgres:
  existingSecret: obstack-stores
  storage:
    size: 20Gi
web:
  existingSecret: obstack-web
  betterAuthUrl: https://obstack.<your-domain>
  explainMode: anthropic  # or fake, the default
  ingress:
    enabled: true
    className: traefik
    host: obstack.<your-domain>
    tls:
      enabled: true
      secretName: obstack-web-tls
ingest:
  ingress:
    enabled: true         # OTLP/HTTP for senders OUTSIDE the cluster only
    className: traefik
    host: otlp.<your-domain>
    tls:
      enabled: true
      secretName: obstack-otlp-tls
```

Your application's pods send to the ingest Service inside the cluster —
`http://<release>-ingest.<namespace>.svc:4318` — and never need the Ingress;
ingest's Ingress is for senders outside it (a laptop, a CI job posting a
change event), HTTP only, since gRPC is deliberately not exposed. The web origin
must be the `https://` one a browser reaches: it is what upgrades the session
cookie to its `__Secure-` name, and a wrong value here is a login that never
sticks.

### 3. TLS

`web.ingress.tls.secretName` and `ingest.ingress.tls.secretName` name
`kubernetes.io/tls` Secrets the chart never renders. The standard pairing on
k3s is cert-manager with a Let's Encrypt `ClusterIssuer` (HTTP-01 needs port 80
reachable on the node) issuing both hosts; a certificate you already hold,
loaded as the Secret and renewed by you, works the same with zero new
components.

### 4. Install, sign up, and the plan

```bash
helm install obstack deploy/helm/obstack -f pilot-values.yaml --timeout 900s --wait
kubectl get jobs                                          # both migrate Jobs Complete
curl -sI https://obstack.<your-domain>/login | head -1    # 200, over TLS
```

Sign up at `/signup`; the first account creates the workspace, and the General
tab of Settings prints its workspace id.

A fresh workspace is on the `free` plan — the hosted product's quota and
retention (the numbers are on [Billing and plans](/docs/billing-and-plans)) —
and the billing rail that would move it is the hosted product's, not yours:
`OBSTACK_BILLING_MODE` stays `fake` here, so there is no checkout to run. Real
traffic crosses the free quota in hours, and what follows is head sampling and
a short retention sweep — an install evaluating obstack on that plan is
evaluating a throttled one. Move the workspace to `pro` by one row; the row is
the one authority everything reads:

```bash
kubectl exec statefulset/obstack-postgres -- psql -U obstack -d obstack -c \
  "INSERT INTO workspace_plans (workspace_id, plan_id) VALUES ('<workspace id>', 'pro')
   ON CONFLICT (workspace_id) DO UPDATE SET plan_id = 'pro', updated_at = now();"
```

A self-hosted install has no reason to carry the hosted product's plan table at
all; a `self-hosted` plan, or retention as a chart value, is the open question
this row stands in for, and until it is answered the row is the stated posture.

### 5. The two keys: the seeded one and the one you issue

The Postgres migrations seed `ok_dev_local` — a public credential, printed in
this repository — so that a clean boot has a key for the collector, the demo
pod and every harness. Once ingest's Ingress is up, that is a write door anyone
can open into `ws_demo`: not your workspace, but your ClickHouse, your quota
and a log stream nobody asked for. Right after signing up, in this order:

1. Issue an `ingest` key in Settings → API keys (the default scope; the key is
   shown once).
2. Put it in a Secret and point the collector at it — since 0.7.0 the chart
   reads the key from a Secret and never carries it in a values file:

   ```bash
   kubectl create secret generic obstack-collector --from-literal=collector-api-key='<the issued key>'
   ```

   ```yaml
   collector:
     existingSecret: obstack-collector
   demo:
     enabled: false        # the seeded key's other user
   ```

   `helm upgrade obstack deploy/helm/obstack -f pilot-values.yaml --timeout 300s --wait`
   rolls both collector pods onto your key and removes the demo pod.
3. Revoke the seed:

   ```bash
   kubectl exec statefulset/obstack-postgres -- psql -U obstack -d obstack -c \
     "UPDATE api_keys SET revoked_at = now() WHERE id = 'key_dev_local';"
   ```

   Ingest caches lookups for 30 seconds, which is how long the old key keeps
   working.

That a real install has to revoke a migration's seed by hand is a known gap; a
chart-driven revocation, or a seed that only exists under a dev flag, are the
alternatives, and this recipe is the stated posture until one is ruled.

### 6. Your application

Two instrumentation paths, both already documented and both landing the same
four layers: an obstack SDK from source ([Quickstart](/docs/quickstart)), or
plain OpenTelemetry pointed at the in-cluster ingest Service with the issued
key as a bearer header ([Bring your own OTel](/docs/sdks/bring-your-own-otel)).
The collector needs nothing from your manifests: the DaemonSet tails every
pod's stdout on its node and scrapes the kubelet, the cluster collector ships
events and cluster state, and `/app/infra` and each trace's timeline render
your namespaces as they are.

The exit: one request through your service, and its trace resolves at
`/app/traces/<id>` with its layers, the prompt and completion on the `llm`
span, a cost priced at ingest, and the collector's correlated logs beside it.

### 7. Explain on the cluster

`web.explainMode` is `fake` unless you set it: the panel explains a trace with
the fake provider and says so. `anthropic`, with the key in the web Secret's
`explain-api-key`, makes Explain and incident RCA real; runs are metered per
plan, and a missing key is a per-request refusal, never a boot failure. A value
outside those two fails `helm template`.

### 8. A developer's coding agent over MCP

`/mcp` is a path on the web Service and rides the web Ingress — nothing else to
expose. With `web.ingress.enabled` the chart sets `OBSTACK_PUBLIC_MCP_ENDPOINT`
to `https://<host>/mcp`, so `/app/mcp` prints the real address in every
client's setup line. Issue a key with the scope `read` and follow
[MCP for coding agents](/docs/mcp); the key can be revoked from the same tab,
and nothing over that door writes.

### 9. Backups

Backup automation is not in the chart, so bring the smallest honest one, in
this order: the VM's own disk snapshot on the hypervisor's schedule (k3s's
`local-path` volumes are directories under `/var/lib/rancher/k3s/storage`),
then a nightly `pg_dump` of Postgres copied off the node — it holds what people
authored and nothing can re-derive: identity, keys, incidents, alerts,
dashboards. ClickHouse holds telemetry that retention already treats as
expiring; an install that wants store-level backups anyway turns on
`clickhouse.backups.enabled`, which declares a `backups` disk (its own volume
with `clickhouse.backups.existingClaim`, or a staging directory on the data
volume by default) for `BACKUP DATABASE obstack TO Disk('backups', …)`. The
chart README's "Backups" section has the loop and what it measured.

### 10. Upgrades, and the first numbers

An upgrade is a reviewed values file with a new sha and digest, then
`helm upgrade obstack deploy/helm/obstack -f pilot-values.yaml --timeout 300s --wait`.
The migrate Jobs run as `pre-upgrade` hooks and the serving pods refuse to
start on an unapplied schema, so a forgotten migration is loud; never run
`ingest migrate` by hand beside the Job — exactly one runner per upgrade.
After a day of real traffic, record what the node actually uses (CPU and
memory per pod, ClickHouse disk growth per day): the chart's requests are
stated defaults, and these are the first measurements a real install produces.

## Upgrading from 0.2.0 is a reinstall, and it destroys data

0.3.0 replaced the ClickHouse and Postgres Deployment-plus-hostPath shape with
StatefulSets and PersistentVolumeClaims. **There is no upgrade path from a
pre-0.3.0 release, and none is being built.**

`helm upgrade` across that boundary now **refuses outright**, and it used not
to — which was exactly the danger. Measured before the guard existed: a
Deployment and a StatefulSet of the same name are different kinds, so Helm
deleted the two Deployments, created the two StatefulSets, and they bound
brand-new, empty PVCs. The release reported `Upgrade complete` in 28 seconds
with `--wait` green while both stores were empty, and the old data sat on the
node with nothing reading it. Silent-green data loss, not a failure anyone would
see coming.

The templates now look the live cluster up at render time and fail the whole
release before Helm touches anything. Moving across the boundary is a deliberate
uninstall:

```bash
helm uninstall <release>
# On a real node that survives, the OLD chart's per-node directories are not a
# release resource and are not removed by helm — clean them by hand:
#   rm -rf /var/lib/obstack-clickhouse/<release> /var/lib/obstack-postgres/<release>
helm install <release> deploy/helm/obstack   # 0.3.0+, from empty PVCs
```

Nothing there is a data migration. The fresh install's migrate Jobs apply the
schema to empty volumes exactly as a brand-new install always has.

## Migrations: exactly one runner per upgrade

There is no lock around the migrations and there is deliberately never going to
be one, so the rule is structural: **exactly one process applies migrations per
upgrade.** Compose gets that for free with its single container. Kubernetes
cannot, because the natural replica count is two or more and every replica would
boot into the same DDL — so the chart splits the roles. A Job runs the ClickHouse
migrations and a second runs the Postgres set; the serving Deployment runs with
`OBSTACK_MIGRATE_ON_BOOT=false`.

That flag does **not** mean "skip migrations". Those pods still check the schema
before they bind anything and refuse to start if any version the binary carries
is unapplied, so a chart that forgets its Job crash-loops loudly instead of
serving queries against a table missing columns.

Each Job's lifecycle differs by operation — a normal Job on install, a
`pre-upgrade` hook on upgrade — because on an install the database does not
exist yet for a hook to run against.

## Credentials and rotation

Every credential the chart handles resolves through the same pattern. By default
the chart renders its own Secret from the values; setting
`clickhouse.existingSecret`, `postgres.existingSecret`, `web.existingSecret`,
`ingest.existingSecret` or `collector.existingSecret` sources that group from a
Secret already in the cluster instead.

**Those values are a NAME, never a value.** The credential itself never has to
pass through `values.yaml`, `--set`, or the release manifest. Key names are
fixed by the chart rather than values-configurable, so a brought Secret has
exactly one thing to get right instead of two: `clickhouse-ingest-password`,
`clickhouse-web-password`, `postgres-password`, `better-auth-secret`,
`explain-api-key`, `vercel-drain-secret`, `collector-api-key`. The Explain key
and the drain secret are read as optional, so a brought Secret may omit either
entirely; the collector's key is not — a collector with no key holds in
`CreateContainerConfigError` rather than sending an empty bearer.

Five groups, not seven: ClickHouse's two users rotate together, the web
workload's two auth slots are a third group, `ingest`'s one optional slot is a
fourth because it rotates with a drain's configuration in somebody else's
dashboard, and the collector's key is a fifth because the product issues it and
it rotates from Settings, on the product's schedule rather than any store's.
**No external-secrets integration ships here** — the name override is the whole
mechanism.

**Rotation is a documented procedure, never automated, and it differs by
credential:**

- **ClickHouse** (`clickhouse.ingestPassword`, `clickhouse.webPassword`). Both
  users are defined in a config file with the password read from the
  environment; there is no `ALTER USER` to run. Update the Secret, then roll the
  pod: `kubectl rollout restart statefulset/<release>-clickhouse`. Changing the
  value on the chart's own Secret rolls it for you on the next `helm upgrade`
  through a checksum annotation, but rotating an `existingSecret` is invisible
  to Helm at render time, so that roll is always the manual command. **Roll
  `deployment/<release>-ingest` as well, on either path** — its pods read the
  password through a `secretKeyRef`, and a reference's name and key do not
  change when the Secret's data does. A ClickHouse that came back on the new
  password while ingest still holds the old one fails every insert until those
  pods restart.
- **Postgres** (`postgres.password`). The image reads `POSTGRES_PASSWORD` at
  initdb time only, so a Secret update alone rotates nothing on a cluster whose
  data directory already exists. Rotating for real is two steps, in order:
  `ALTER USER obstack WITH PASSWORD '<new>'` against the live database, then
  update the Secret and roll `statefulset/<release>-postgres` **and**
  `deployment/<release>-ingest`.
- **The web workload's two slots** (`web.betterAuthSecret`, `web.explainApiKey`).
  Update the Secret and roll `deployment/<release>-web`. Rotating the auth secret
  invalidates every live session; users sign in again.
- **The collector's key** (`collector.apiKey`, `collector.existingSecret`). Issue
  a new `ingest` key in Settings → API keys, update the Secret, roll
  `daemonset/<release>-collector` **and** `deployment/<release>-collector-cluster`,
  then revoke the old key on the same page. On the chart's own Secret a
  `helm upgrade` with the new `collector.apiKey` rolls both for you; a brought
  Secret's rotation is invisible to Helm, so there the roll is the two commands.

## Managed Postgres

`postgres.managed.enabled` points ingest and web at a Postgres this chart does
not run. `postgres.managed.dsn` replaces the in-chart host half of both DSNs,
and the password still resolves through the same `postgres-password` Secret key,
since a managed DSN never carries one. That DSN's contract is strict: exactly
one `@`, and no password component.

Enabling it **disables** the in-chart Postgres rather than idling it — the
StatefulSet, both its Services and its wait init containers stop rendering
entirely — and **retargets the pg-migrate Job** at the managed DSN, so the
operator's Postgres receives the schema through the same one-runner Job every
install has always used. **The Job failing IS the reachability gate, by
design:** the install's `--wait` fails loudly at pg-migrate when the managed
target is unreachable, and there is deliberately no second preflight mechanism
for the same fact.

**The stated ceiling:** this is verified in kind against an out-of-release
Postgres simulating the brought DSN. Verification against a real managed
provider — TLS and `sslmode`, provider auth — cannot exist in kind and has not
been done; it arrives with the hosting decision.

## Shutdown

The ingest Deployment sets `terminationGracePeriodSeconds: 45`. The shutdown
ladder's stated worst case is the write deadline (10s) plus one in-flight retry
attempt (up to 30s), and 45s leaves margin on top for the receiver and admin
server to unwind. A batch still unwritten when the deadline runs out is
**counted as dropped under the `shutdown` reason**, never lost silently. The
compose bundle uses the same 45 seconds.
