# Self-hosting with the Helm chart

The chart installs the obstack stack on Kubernetes: ClickHouse and Postgres as
StatefulSets with PersistentVolumeClaims, the ingest Deployment plus its two
migration Jobs, the web workload, the `obstack-collector` DaemonSet, and a demo
app pod.

{/* D450/D451/D465 */}

Since chart 0.6.0 the collector also reports the cluster it runs on: the
DaemonSet scrapes its own node's kubelet, and a single-replica cluster
collector (behind `collector.cluster.enabled`, default on — the same workload
that ships Kubernetes events) watches the API server, so `/app/infra` renders
the release's own nodes and pods with no extra configuration. The seventeen
metric names it is fenced to, the RBAC both receivers need and the per-node
series budget are in `deploy/collector/README.md` under "Kubernetes metrics".
0.6.0 is a **non-additive** bump: the old `k8sEvents` values block became
`collector.cluster.*` with deliberately no alias — a values file still setting
the old key is silently ignored and the collector comes up enabled — and the
singleton's objects renamed `<release>-collector-events` →
`<release>-collector-cluster`; the chart README's "Upgrading to 0.6.0" section
has both rules.

## Install

The chart lives in this repository — there is no chart repository to add — and
runs from images this repository builds, so build and load them into the cluster
first.

```bash
helm install obstack deploy/helm/obstack --timeout 900s --wait \
  --set "web.betterAuthSecret=$(openssl rand -base64 32)"
```

`900s` is the migrate Job's own deadline, which already contains a cold
ClickHouse pull; a warm node is done in about 18 seconds.

`web.betterAuthSecret` is the one value with no default — a committed
cookie-signing secret in a distributable chart is a shipped vulnerability — and
it is not optional: a live-stamped web image booted without it refuses to serve,
so `--wait` would sit on a crash-looping pod until the timeout. Set
`web.betterAuthUrl` to the origin a browser reaches the deployment on.

Real deployments replace the local images with the published ones, pinned by
tag and digest, with `web.pullPolicy` and `ingest.pullPolicy` set to
`IfNotPresent` — the next section.

## Installing from the published images

Every merge to master publishes the images this repository builds to GHCR,
tagged by the merge commit and nothing else — no `latest`, no `master`, so a
values file always names the exact bytes CI built and refusal-tested:

| chart value | published tag |
|---|---|
| `web.image` | `ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>` — the live-stamped variant; the `mock-sha-` one is the public demo and refuses to serve live |
| `ingest.image` | `ghcr.io/ziadabdelsalam/obstack-ingest:sha-<sha>` |
| `demo.image` | `ghcr.io/ziadabdelsalam/obstack-demo-agent:sha-<sha>` — since chart 0.7.0, needed only while `demo.enabled` is true |

`<sha>` is the full 40-character merge commit. Pin the digest as well; it is
printed in the `publish` job's step summary, or resolved by a pull:

```bash
docker pull ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>
```

and write `image: ghcr.io/ziadabdelsalam/obstack-web:live-sha-<sha>@sha256:<digest>`.
Two facts before the first pull: the images are `linux/amd64` (an arm64 node
cannot run them), and the packages answer `401` to anonymous pulls until their
visibility is set to public on GitHub — per package, not per repository. The
chart ships no `imagePullSecrets` support; public packages are the posture.

## What the chart does and does not cover

In scope, and shipped: ClickHouse and Postgres with durable storage, the ingest
Deployment and its migration Jobs, the web workload, the collector DaemonSet and
the single-replica cluster collector, a demo pod behind `demo.enabled`, a
chart-owned Secret with an `existingSecret` override on every credential
(five groups since 0.7.0 — the collector's key included), optional Ingress for
web and for ingest's OTLP/HTTP surface, `web.explainMode`, an optional
`backups` disk for ClickHouse, and resource requests and limits on ingest, web,
both collectors and both demo containers, with requests only on the two stores.

Deliberately **not** in scope, and not a gap to fill quietly: HA beyond ingest's
existing replica story, autoscaling, PodDisruptionBudgets, NetworkPolicies,
multi-replica ClickHouse, backup automation, an ingress controller,
cert-manager, and pull secrets. Limits are deliberately **not** set on
ClickHouse and Postgres: sizing a database's limits is a measurement, not a
guess, and a wrong limit OOM-kills the store it was meant to protect.

`ingest.replicaCount` defaults to 2. Enabling ingest's Ingress exposes the
OTLP/HTTP surface and automatically sets `OBSTACK_PUBLIC_OTLP_HTTP_ENDPOINT` on
the web workload, so the product's quickstart renders that address; **gRPC is
deliberately not exposed**, and a deployment that publishes only HTTP gets an
honest omission in the quickstart rather than an address nothing serves. No
ingress controller and no cert-manager ship here — `web.ingress.enabled` and
`ingest.ingress.enabled` assume one already exists in the cluster.

## The first install on a real cluster, in order

The chart's defaults are a kind cluster's. A cluster people will sign in to
needs six things the defaults do not do, in this order; each is a value in the
chart or a row in its Postgres, and none is a new component.

1. **A values file with no credential in it.** One brought Secret per group
   you own (`clickhouse.existingSecret`, `postgres.existingSecret`,
   `web.existingSecret`, `ingest.existingSecret`, `collector.existingSecret`,
   with the fixed key names under "Credentials and rotation" — the auth
   secret lives in the web Secret's `better-auth-secret`, generated once with
   `openssl rand -base64 32`); the published images by tag and digest;
   `web.betterAuthUrl` as the `https://` origin browsers will use (the
   `https://` is what upgrades the session cookie to its `__Secure-` name — a
   wrong value here is a login that never sticks); `web.ingress` and
   `ingest.ingress` enabled with their hosts and TLS Secrets; and the storage
   sizes from your expected event volume and plan retention rather than the
   20Gi/10Gi dev defaults. Before the cluster sees the file, run the chart's
   budget check against it — a request set that does not fit the node's
   allocatable leaves the install's `--wait` hanging for the whole timeout,
   and nothing names the cause:

   ```bash
   npx tsx --tsconfig apps/web/tsconfig.json --conditions react-server \
     deploy/helm/obstack/acceptance.ts budget -f your-values.yaml
   ```

2. **Install, and sign up.** `helm install obstack deploy/helm/obstack -f your-values.yaml --timeout 900s --wait`;
   both migrate Jobs reach `Complete`; `https://<web.ingress.host>/login`
   answers 200 over TLS; the first signup creates the organization and the
   workspace. Settings → General shows the workspace id the next step needs.

3. **Move the workspace off `free`.** A fresh workspace is on the `free` plan —
   50,000 events a month and 7-day retention — with no row needed to be on it
   and no billing rail on a self-hosted install to change it: the billing mode
   is `fake`, and the hosted product's checkout is its merchant's, not yours.
   Real traffic crosses 50,000 events in hours, after which ingest head-samples
   the rest and a 7-day sweep keeps a week — the install would be evaluated
   throttled and short of memory with nobody told. One row is the whole
   authority:

   ```bash
   kubectl exec statefulset/obstack-postgres -- psql -U obstack -d obstack -v ON_ERROR_STOP=1 \
     -c "INSERT INTO workspace_plans (workspace_id, plan_id) VALUES ('<workspace id>', 'pro') ON CONFLICT (workspace_id) DO UPDATE SET plan_id = 'pro', updated_at = now();"
   ```

   `pro` is 1,000,000 events a month and 30-day retention. A self-hosted plan
   with no quota is a product decision the chart does not take; until it is
   taken, this row is the documented posture.

4. **Issue the collector's key, then upgrade with it.** The install is
   two-step by construction: the collector sends a bearer key that must be an
   `api_keys` row in this release's Postgres, and no key exists before a
   workspace does. Settings → API keys → issue a key with scope `ingest`, put
   it in your collector Secret under `collector-api-key` (or in
   `collector.apiKey` if the chart owns that Secret), and
   `helm upgrade obstack deploy/helm/obstack -f your-values.yaml --timeout 300s --wait`.
   Both collectors roll and ship into your workspace from then on; until this
   step they were shipping into `ws_demo` under the seeded dev key.

5. **Turn the demo off.** `demo.enabled: false`, same upgrade. Keep it on
   exactly as long as you want the four-layer proof from something that is not
   yet your own service — a `/chat` against the demo Service through a
   port-forward, the trace resolving in the product with `api`, `agent`,
   `tool` and `llm` under one id. The moment your own instrumented service has
   done the same, the pod is noise, a CPU request and a writer into `ws_demo`.

6. **Revoke the seeded dev key — last, because steps 4 and 5 depend on the
   row.** The Postgres migrations seed `ok_dev_local` for `ws_demo` in every
   install: a public credential by design, printed in the repository, and the
   row the chart's collector and demo pod authenticate with out of the box.
   Once ingest's Ingress is up, anyone reading the repository can POST
   telemetry into your cluster's `ws_demo` — not a read of your data, but a
   write into your ClickHouse and a quota sink nobody asked for.

   ```bash
   kubectl exec statefulset/obstack-postgres -- psql -U obstack -d obstack -v ON_ERROR_STOP=1 \
     -c "UPDATE api_keys SET revoked_at = now() WHERE id = 'key_dev_local';"
   ```

   Ingest caches key lookups for 30 seconds, positive and negative, which is
   how long the revoked key keeps working.

## TLS

The chart never issues or renders certificate material: `web.ingress.tls.secretName`
and `ingest.ingress.tls.secretName` name a `kubernetes.io/tls` Secret already in
the cluster, and `web.ingress.className` / `ingest.ingress.className` pick the
controller the cluster already runs. On k3s that controller is Traefik, and the
standard pairing is cert-manager with a Let's Encrypt `ClusterIssuer` issuing
both hosts — HTTP-01 needs port 80 reachable on the node for the challenge. A
certificate you already hold, loaded as the Secret and renewed by you, is the
zero-new-components alternative; nothing in the chart cares which.

## Backups

Backup automation is out of the chart by ruling, and the honest floor on a
single node is three things:

- **The node's own disk snapshot** on the hypervisor's schedule. Both PVCs are
  directories on the node under a single-node storage class such as k3s's
  `local-path`, which has no volume snapshots; a whole-node snapshot is
  consistent enough for a pilot and costs no new component.
- **A nightly `pg_dump`, copied off the node.** Postgres holds the rows a person
  authored and no machine can re-derive — identity, keys, incidents, alerts,
  dashboards, the plan row. The smallest honest version is a CronJob in your
  own namespace on the same Postgres image the chart pins:

  ```yaml
  apiVersion: batch/v1
  kind: CronJob
  metadata:
    name: obstack-pg-dump
  spec:
    schedule: "15 2 * * *"
    concurrencyPolicy: Forbid
    jobTemplate:
      spec:
        template:
          spec:
            restartPolicy: Never
            containers:
              - name: pg-dump
                image: postgres:17.11
                env:
                  - name: PGPASSWORD
                    valueFrom:
                      secretKeyRef:
                        name: obstack-credentials   # or your postgres existingSecret
                        key: postgres-password
                command:
                  - sh
                  - -c
                  - |
                    set -eu
                    f="/backup/obstack-$(date -u +%Y%m%dT%H%M%SZ).sql.gz"
                    pg_dump -h obstack-postgres -U obstack obstack | gzip > "$f"
                    # copy "$f" off the node here — an object store, another
                    # machine; a dump on this node's disk is not yet a backup
                volumeMounts:
                  - name: backup
                    mountPath: /backup
            volumes:
              - name: backup
                persistentVolumeClaim:
                  claimName: obstack-pg-dump   # a PVC you create
  ```

- **ClickHouse, when you want more than the snapshot.** `clickhouse.backups.enabled: true`
  declares a `local` disk named `backups` at `clickhouse.backups.path`
  (default `/var/lib/clickhouse/backups/`, on the data volume) and allows
  `BACKUP` and `RESTORE` against it, so from `clickhouse-client` as the
  `obstack_ingest` user

  ```sql
  BACKUP DATABASE obstack TO Disk('backups', 'obstack-20260915.zip')
  ```

  answers with the backup's id and `BACKUP_CREATED`, and the archive sits at
  that path until you copy it off the node. Enabling the flag rolls the
  ClickHouse pod once.

## Explain on Kubernetes

Explain's default mode is `fake` on every deployment, and the chart now states
it: `web.explainMode` renders `OBSTACK_EXPLAIN_MODE`, and the panel says, on
every trace and incident, that this deployment runs the fake provider — never
a fabricated summary presented as real. `web.explainMode: anthropic` with the
key in the web Secret's `explain-api-key` makes Explain and incident analysis
real; runs spend the workspace plan's monthly Explain allowance. Any other value
is refused when the chart renders. [The Explain page](/docs/explain) has the
provider variables.

## Coding agents over MCP

With `web.ingress.enabled` on, the web Deployment carries
`OBSTACK_PUBLIC_MCP_ENDPOINT` — `https://<web.ingress.host>/mcp`, or `http://`
when the Ingress has no TLS — so the product's MCP page prints the real address
and the client setups it renders are copy-ready. `/mcp` is a path on the web
Service the Ingress already routes; nothing new is exposed. A developer issues a
key at scope `read` in Settings → API keys and adds the server to their client;
the endpoint refuses `ingest` keys and ingest refuses `read` keys, so the two
credentials cannot be confused. [MCP for coding agents](/docs/mcp) has the
rest.

## Upgrading from 0.2.0 is a reinstall, and it destroys data

0.3.0 replaced the ClickHouse and Postgres Deployment-plus-hostPath shape with
StatefulSets and PersistentVolumeClaims. **There is no upgrade path from a
pre-0.3.0 release, and none is being built.**

`helm upgrade` across that boundary now **refuses outright**, and it used not
to — which was exactly the danger. Measured before the guard existed: a
Deployment and a StatefulSet of the same name are different kinds, so Helm
deleted the two Deployments, created the two StatefulSets, and they bound
brand-new, empty PVCs. The release reported `Upgrade complete` in 28 seconds
with `--wait` green while both stores were empty, and the old data sat on the
node with nothing reading it. Silent-green data loss, not a failure anyone would
see coming.

The templates now look the live cluster up at render time and fail the whole
release before Helm touches anything. Moving across the boundary is a deliberate
uninstall:

```bash
helm uninstall <release>
# On a real node that survives, the OLD chart's per-node directories are not a
# release resource and are not removed by helm — clean them by hand:
#   rm -rf /var/lib/obstack-clickhouse/<release> /var/lib/obstack-postgres/<release>
helm install <release> deploy/helm/obstack   # 0.3.0+, from empty PVCs
```

Nothing there is a data migration. The fresh install's migrate Jobs apply the
schema to empty volumes exactly as a brand-new install always has.

## Migrations: exactly one runner per upgrade

There is no lock around the migrations and there is deliberately never going to
be one, so the rule is structural: **exactly one process applies migrations per
upgrade.** Compose gets that for free with its single container. Kubernetes
cannot, because the natural replica count is two or more and every replica would
boot into the same DDL — so the chart splits the roles. A Job runs the ClickHouse
migrations and a second runs the Postgres set; the serving Deployment runs with
`OBSTACK_MIGRATE_ON_BOOT=false`.

That flag does **not** mean "skip migrations". Those pods still check the schema
before they bind anything and refuse to start if any version the binary carries
is unapplied, so a chart that forgets its Job crash-loops loudly instead of
serving queries against a table missing columns.

Each Job's lifecycle differs by operation — a normal Job on install, a
`pre-upgrade` hook on upgrade — because on an install the database does not
exist yet for a hook to run against.

## Credentials and rotation

Every credential the chart handles resolves through the same pattern. By default
the chart renders its own Secret from the values; setting
`clickhouse.existingSecret`, `postgres.existingSecret`, `web.existingSecret`,
`ingest.existingSecret` or `collector.existingSecret` sources that group from a
Secret already in the cluster instead.

**Those values are a NAME, never a value.** The credential itself never has to
pass through `values.yaml`, `--set`, or the release manifest. Key names are
fixed by the chart rather than values-configurable, so a brought Secret has
exactly one thing to get right instead of two: `clickhouse-ingest-password`,
`clickhouse-web-password`, `postgres-password`, `better-auth-secret`,
`explain-api-key`, `vercel-drain-secret`, `collector-api-key`. `explain-api-key`
and `vercel-drain-secret` are read as optional, so a brought Secret may omit
either entirely.

Five groups, not seven: ClickHouse's two users rotate together, the web
workload's two auth slots are a third group, `ingest`'s one optional slot is a
fourth because it rotates with a drain's configuration in somebody else's
dashboard, and the collector's key is a fifth because it is a client credential
issued in the product's own settings and rotated by revoking and reissuing
there. **No external-secrets integration ships here** — the name override is
the whole mechanism.

**Rotation is a documented procedure, never automated, and it differs by
credential:**

- **ClickHouse** (`clickhouse.ingestPassword`, `clickhouse.webPassword`). Both
  users are defined in a config file with the password read from the
  environment; there is no `ALTER USER` to run. Update the Secret, then roll the
  pod: `kubectl rollout restart statefulset/<release>-clickhouse`. Changing the
  value on the chart's own Secret rolls it for you on the next `helm upgrade`
  through a checksum annotation, but rotating an `existingSecret` is invisible
  to Helm at render time, so that roll is always the manual command. **Roll
  `deployment/<release>-ingest` as well, on either path** — its pods read the
  password through a `secretKeyRef`, and a reference's name and key do not
  change when the Secret's data does. A ClickHouse that came back on the new
  password while ingest still holds the old one fails every insert until those
  pods restart.
- **Postgres** (`postgres.password`). The image reads `POSTGRES_PASSWORD` at
  initdb time only, so a Secret update alone rotates nothing on a cluster whose
  data directory already exists. Rotating for real is two steps, in order:
  `ALTER USER obstack WITH PASSWORD '<new>'` against the live database, then
  update the Secret and roll `statefulset/<release>-postgres` **and**
  `deployment/<release>-ingest`.
- **The web workload's two slots** (`web.betterAuthSecret`, `web.explainApiKey`).
  Update the Secret and roll `deployment/<release>-web`. Rotating the auth secret
  invalidates every live session; users sign in again.
- **The collector's key** (`collector.apiKey`, since 0.7.0). Both collector
  workloads read it through a `secretKeyRef`. Issue the new key in Settings →
  API keys, update the Secret, roll `daemonset/<release>-collector` **and**
  `deployment/<release>-collector-cluster` (the collector reads its environment
  once, at process start), then revoke the old key in the same tab. Changing the
  value on the chart's own Secret rolls both for you on the next `helm upgrade`
  through a checksum annotation; a brought `existingSecret` needs the manual
  roll, like every other group.

## Managed Postgres

`postgres.managed.enabled` points ingest and web at a Postgres this chart does
not run. `postgres.managed.dsn` replaces the in-chart host half of both DSNs,
and the password still resolves through the same `postgres-password` Secret key,
since a managed DSN never carries one. That DSN's contract is strict: exactly
one `@`, and no password component.

Enabling it **disables** the in-chart Postgres rather than idling it — the
StatefulSet, both its Services and its wait init containers stop rendering
entirely — and **retargets the pg-migrate Job** at the managed DSN, so the
operator's Postgres receives the schema through the same one-runner Job every
install has always used. **The Job failing IS the reachability gate, by
design:** the install's `--wait` fails loudly at pg-migrate when the managed
target is unreachable, and there is deliberately no second preflight mechanism
for the same fact.

**The stated ceiling:** this is verified in kind against an out-of-release
Postgres simulating the brought DSN. Verification against a real managed
provider — TLS and `sslmode`, provider auth — cannot exist in kind and has not
been done; it arrives with the hosting decision.

## Shutdown

The ingest Deployment sets `terminationGracePeriodSeconds: 45`. The shutdown
ladder's stated worst case is the write deadline (10s) plus one in-flight retry
attempt (up to 30s), and 45s leaves margin on top for the receiver and admin
server to unwind. A batch still unwritten when the deadline runs out is
**counted as dropped under the `shutdown` reason**, never lost silently. The
compose bundle uses the same 45 seconds.
